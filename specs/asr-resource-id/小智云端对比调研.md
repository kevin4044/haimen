# 小智云端 vs haimen 自建后端 —— 延迟与音质对比调研

> 调研对象：[xinnan-tech/xiaozhi-esp32-server](https://github.com/xinnan-tech/xiaozhi-esp32-server)（社区复刻版，333MB，含模型）
> 对比对象：我们的 haimen fork（v0.12.1 + openai provider + ASR resource_id 修复）
> 结论：**差距几乎全部来自几个具体参数，不是架构问题**

---

## 一、总体结论

小智云端体验好，主要靠三件事：

```
① 判停极其激进但可靠
   · 豆包服务端 VAD:  end_window_size = 200ms
   · 本地 Silero 神经 VAD 兜底 = 1000ms
   → 用户说完 200ms 就开始处理

② 首句播放几乎不等待
   · PRE_BUFFER_COUNT = 5（300ms）
   · 首句只等 2 帧（120ms）
   → 比我们的 600ms 快 300-480ms

③ 用虚拟播放时钟控制帧节奏
   · AudioRateController：计算"设备播到哪了"，不是"该发第几帧"
   · 队列空恢复时重置时间戳，保持播放连续
   → 不会因为 TTS 断档导致音频挤在一起
```

## 二、参数级对比表

| # | 参数 | 小智复刻版 | 我们的 haimen | 差距 |
|---|---|---|---|---|
| **1** | **豆包 `end_window_size`** | **200 ms** ✅ | **1500 ms** ⚠️ | **−1300 ms** |
| **2** | **本地 VAD 静音窗口** | Silero `1000 ms` ✅ | 能量 `MAX_SILENCE_FRAMES=40` = **2400 ms** ⚠️ | **−1400 ms** |
| **3** | **本地 VAD 类型** | **Silero ONNX 神经网络** ✅ | 纯 RMS 能量阈值（1500）⚠️ | 准确度 |
| **4** | **预缓冲帧数** | **5 帧 = 300 ms** ✅ | **10 帧 = 600 ms** ⚠️ | **−300 ms** |
| **5** | **首句播放等待** | **2 帧 = 120 ms** ✅ | 全部 10 帧 = 600 ms ⚠️ | **−480 ms** |
| **6** | `force_to_speech_time` | 未设置（默认） | **1000 ms** ⚠️ | 短指令要多等 1 秒 |
| **7** | 帧节奏控制 | `AudioRateController`（虚拟播放位置）✅ | `next_send_at` 累加 60ms（简单）⚠️ | **卡顿** |
| **8** | 唤醒后 VAD 抑制 | 忽略 2 秒 ✅ | 未实现 ⚠️ | 唤醒词尾音误判 |
| **9** | 无语音超时 | `close_connection_no_voice_time: 120` s | `no_speech_timeout_ms: 10000` = 10 s | 策略不同 |

### 关键结论

```
实际判停延迟（谁先触发算谁）：
  我们: min(豆包 1500, 本地 2400) = 1500 ms  ← 豆包服务端 VAD 先触发
  小智: min(豆包 200,  Silero 1000) = 200 ms
  → 差 1.3 秒
```

## 三、三个值得抄的设计

### ① 双 VAD 架构（服务端 + 本地神经网络）

小智的做法：

```
豆包服务端 VAD:  end_window_size = 200ms   ← 快，但依赖网络
本地 Silero VAD: 1000ms                     ← 慢一点，但本地，兜底

哪个先触发就用哪个 → 200ms 就能判停，且有兜底
```

我们的做法：

```
豆包服务端 VAD:  end_window_size = 1500ms  ← 太保守
本地能量 VAD:    2400ms                     ← 更保守
→ 两个都慢，取最小值还是 1500ms
```

**为什么小智敢用 200ms？**

```
因为它的本地 VAD 是 Silero 神经网络：
  · 能区分"人声"和"环境噪音"（空调、风扇、电视）
  · 不受音量影响（轻声说话也能识别）
  → 所以不需要靠"长时间静音"来兜底误判

我们的能量 VAD：
  · 环境噪音 → 能量高 → 误判"还在说话"
  · 所以只能用很长的窗口兜底 → 2400ms
```

**这是"组件选得对"带来的收益，不是参数调得好** ✅

### ② 虚拟播放时钟（AudioRateController）

```python
class AudioRateController:
    self.play_position = 0        # 虚拟播放位置（毫秒）
    self.start_timestamp = None
    
    # 队列空恢复时重置时间戳，保持播放时间连续
    # 这样工具调用等待期间，新加入的音频不会提前播放
    if elapsed_since_empty >= self.interval_ms:
        self.start_timestamp = time.monotonic() - (self.play_position / 1000)
```

核心思想：**维护一个"设备当前播到哪一刻"的虚拟时钟**，Sender 按这个时钟填充队列。

好处理的问题：
- **TTS 断档**（比如工具调用时）→ 队列空了，恢复时重置时间戳，不会让后面的音频提前播
- **发送抖动** → 按绝对时刻对齐，不会累积误差
- **并发** → 多个 TTS 句子不会互相干扰

我们的 `next_send_at` 累加：
- ✅ 解决了累积误差
- ⚠️ 但没有"播放位置"概念，断档恢复时是简单粗暴的"重新对齐"

### ③ 首句极速播放

```python
# 小智
PRE_BUFFER_COUNT = 5                        # 300ms 预缓冲
playback_time = 2 * interval_ms / 1000.0    # 首句只等 2 帧 = 120ms

# 我们
PREBUFFER_COUNT = 10                        # 600ms 预缓冲
# 首句也要等满 10 帧 = 600ms
```

**首句 480ms 的差距，用户感知很明显** ✅

## 四、建议的实施顺序

### 阶段 1：改参数（收益最大、风险最低）

```rust
// ── src/xiaozhi_asr_llm_tts.rs ──

// ① 豆包服务端 VAD：1500 → 200（对齐小智）
+ end_window_size: Some(200),

// ② force_to_speech_time：1000 → 200（短指令不再多等）
+ force_to_speech_time: Some(200),

// ③ 本地能量 VAD 兜底：40 帧（2400ms）→ 20 帧（1200ms）
- const MAX_SILENCE_FRAMES: u64 = 40;
+ const MAX_SILENCE_FRAMES: u64 = 20;

// ④ 能量阈值提高（更敏感）
- const SILENCE_RMS_THRESHOLD: f64 = 1500.0;
+ const SILENCE_RMS_THRESHOLD: f64 = 2000.0;

// ── crates/haimen-xiaozhi/src/ws.rs ──

// ⑤ 预缓冲 10 → 5 帧（600ms → 300ms）
- const PREBUFFER_COUNT: usize = 10;
+ const PREBUFFER_COUNT: usize = 5;
```

**预期收益：约 −1.6 秒**（1500→200 是 −1300，预缓冲 −300）

**⚠️ 风险**：
- 200ms 可能偏激进 —— 如果你说话中间有 200ms 以上的停顿，会被切断
- 建议 **从 400-500ms 起步**，用几天没问题再降到 200

### 阶段 2：引入神经 VAD（收益中等、成本中等）

```
方案 A：集成 Silero VAD（Rust 版）
  · ort (ONNX Runtime) crate + silero_vad.onnx 模型（~2MB）
  · 替换当前的 compute_pcm_rms 能量判断
  · 收益：可以用更短的窗口（800-1000ms）而不误判
  · 成本：1-2 天

方案 B：保持能量 VAD，但改进算法
  · 加"噪声底跟踪"（自适应阈值）
  · 加"双阈值滞回"（进入/退出语音用不同阈值）
  · 成本：半天
  · 收益：比现在好，但不如 Silero
```

### 阶段 3：AudioRateController（解决卡顿）

```
现状：卡顿原因未完全确认（帧节奏 fix 已在 main 里）
待做：
  · 先在真机上开 debug 日志，确认有没有「帧到达断档」
  · 如果确认是断档 → 移植 AudioRateController 的虚拟时钟
```

## 五、需要进一步确认的

### ① 卡顿的真正原因还没定

已知：
- ✅ 帧节奏的 fix 已在 main（`next_send_at` 累加 60ms）
- ✅ DTX 已关闭
- ✅ 日志里没有"断档"警告

未定：
- ⚠️ 需要用户描述具体症状（断续？越说越快？杂音？）
- ⚠️ 或者需要真机抓 debug 日志

### ② 小智云端到底用多少 end_window_size？

复刻版用 200ms，但云端可能不同。**建议实测**：
```
临时把设备切回小智云 → 用手机秒表测"说完到有反应"的时间
→ 反推它的判停参数
```
⚠️ 但切回去要改 OTA 地址，比较麻烦

### ③ force_to_speech_time 的含义

```
"VAD 生效最小音频时长（毫秒）"
→ 意思是录音开始后，至少要积累这么多音频，VAD 才会生效
→ 设 1000ms = 说话不足 1 秒不会被判停
→ 对"开灯"这种两字指令是浪费
```

小智复刻版**没有设置这个参数**（用默认），值得对齐。
