# MQTT + UDP 实现方案

> 目标：让小智设备走 MQTT+UDP 协议，从而支持**服务端主动播报**与**主动问询（问完自动进入聆听）**
> 前提：不改设备固件（协议完全由固件支持，只需在 OTA 响应里下发 MQTT 配置）

---

## 一、为什么做（原因）

### 现状的限制

```
当前架构：设备 ⇄ WebSocket ⇄ haimen
  · WebSocket 是【会话制】—— 设备唤醒时才建立连接，说完就断
  · 服务端无法主动推送任何内容
  · 只能"用户问，设备答"
```

### 想要的能力

| 能力 | 依赖 | 现状 |
|---|---|---|
| **主动播报**（洗衣机洗完了、温度高了） | 服务端能主动推 | ❌ 做不到 |
| **主动问询**（"客厅有点热，要开空调吗？"→ 用户回答） | 服务端能推 + 能让设备进入聆听 | ❌ 做不到 |
| **HA 驱动小智**（HA 自动化里按一下，小智说话） | 同上 | ❌ 做不到 |
| **自主做事**（HA 事件 → 小智行动） | MQTT 作为通道 | ❌ 做不到 |

### 为什么必须是 MQTT

```
固件只支持两种传输模式：
  · WebSocket（会话制 ⚠️）
  · MQTT + UDP（长连接 ✅ + 音频走 UDP）

固件的协议选择逻辑（application.cc:544-559，无 fallback）：
  if (ota->HasMqttConfig())        → MqttProtocol   ← MQTT 优先
  else if (ota->HasWebsocketConfig()) → WebsocketProtocol
  else                              → MqttProtocol

→ 只要 OTA 响应里有 mqtt 段，设备就切到 MQTT
→ 没有"两个都下发、运行时切换"的机制
```

**结论**：要做主动能力，必须走 MQTT；而 MQTT 模式下音频必须走 UDP，
所以**不能"先做播报、后补 UDP"**，必须一次性实现完整协议栈。

## 二、调研发现（关键事实）

### 1. 固件已支持的能力（不需要改固件）

| 能力 | 实现机制 | 出处 |
|---|---|---|
| **主动播报** | `notify` 消息：播放 HTTP URL 的 Ogg Opus，**不需要 UDP** ✅ | `docs/notify.md` |
| **播完自动聆听** | `tts` 消息 `state: stop` → 设备自动 `SetDeviceState(Listening)` | `application.cc:642-651` |
| **打断** | 唤醒词 / 按键可中断播放 | `application.cc` |
| **notify 只在 Idle 生效** | 忙时丢弃，不打断对话 ✅ | `application.cc:1183` |
| **notify 播完回 Idle** | 不会自动听（这是它与 `tts` 的关键差别）⚠️ | `application.cc:1228-1237` |

**这意味着**：
- 只播报 → 用 `notify`（简单，不需要 UDP）
- 播完要等回答 → 必须用 `tts` 会话（需要 UDP）

### 2. HA 侧的基础设施已就绪

```
✅ HA 已装 MQTT 集成，运行的是 Mosquitto broker 加载项
   · 地址：192.168.110.34:1883
   · 状态：loaded ✅
   · 当前完全空闲（5 秒扫描 0 条流量）—— 我们是第一个用户
   
✅ 凭证可用：vdr_runtime / vdr_runtime（已实测 CONNECT/SUB/PUB 全通）

✅ MQTT Discovery 已实测可行：
   发布 homeassistant/sensor/xxx/config + 状态 topic
   → HA 立刻自动创建实体 sensor.haimen_ce_shi_she_bei_...
   → 说明"把小智注册成 HA 设备"这条路是通的
```

### 3. haimen 的代码分层是干净的（重大利好）

```
crates/haimen-xiaozhi/
  ├── protocol.rs  (370 行)  音频帧编解码 / 协议检测   → 【传输无关 ✅ 可复用】
  ├── strategy.rs  (451 行)  AsrTtsStrategy 管线       → 【只依赖 types ✅ 可复用】
  ├── types.rs     (277 行)  共享类型                  → 【可复用 ✅】
  ├── ota.rs       (220 行)  OTA 响应                  → 【只需加 mqtt 段 ✅】
  └── ws.rs        (1616 行) WebSocket 传输层          → 【需要一个 MQTT+UDP 兄弟层 ⚠️】
```

**结论**：不需要重写语音管线，只需要**新增一个传输层**，与 ws.rs 平级，
复用 strategy + protocol。工作量从"1-2 周"降到约 **5-8 天**。

### 4. 协议细节（来自 `docs/mqtt-udp_zh.md` 与固件源码）

```
MQTT 通道：控制消息（JSON）
  · endpoint / client_id / username / password
  · keepalive 默认 240 秒
  · publish_topic：设备发布消息用的主题

UDP 通道：音频（Opus，AES-CTR 加密）
  · 设备发 hello（transport: "udp"）
  · 服务器回 udp: { server, port, key, nonce }
  · 音频包结构：
      |type 1B|flags 1B|payload_len 2B|ssrc 4B|timestamp 4B|sequence 4B|payload|
  · 采样率：上行 16kHz / 下行 24kHz，帧 60ms
  · 序列号单调递增，防重放
```

### 关键设计决策

**① 传输层可切换（保命方案）**

```toml
[xiaozhi]
# websocket（默认，当前可用） 或 mqtt
protocol = "websocket"
```

- **默认保持 `websocket`** → 现有链路不受影响 ✅
- **改成 `mqtt`** → OTA 响应下发 mqtt 段 → 设备切过去
- **出问题改回 `websocket` + 设备重启** → 回退 ✅

**② 复用而非重写**

```
新增文件只做"传输"，不碰语音逻辑：
  · strategy.rs 不动（只可能在需要时加少量 hook）
  · protocol.rs 不动
  · ws.rs 不动（保留作为可切换选项）
```

**③ HA 集成分两层**

```
第一层（必须）：haimen ⇄ HA 的 MQTT
  · MQTT Discovery 注册小智实体
  · HA 可以发指令：播报 / 聆听 / 停止
  · haimen 上报状态：idle / listening / speaking

第二层（可选）：haimen ⇄ 小智设备的 MQTT+UDP
  · 就是本方案的主体
```

## 四、Topic 与消息设计

### 4.1 HA ⇄ haimen（我们自己的主题，与设备协议无关）

```
haimen/xiaozhi/<device_id>/state          haimen → HA（保留消息，QoS 1）
haimen/xiaozhi/<device_id>/stt            haimen → HA（最近识别文本）
haimen/xiaozhi/<device_id>/reply          haimen → HA（最近回复文本）
haimen/xiaozhi/<device_id>/say            HA → haimen（要求播报）
haimen/xiaozhi/<device_id>/listen         HA → haimen（要求开始聆听）
haimen/xiaozhi/<device_id>/stop           HA → haimen（打断）
```

**消息格式**（say）：
```json
{
  "text": "客厅有点热欸，要不要开空调？",
  "then_listen": true,      // 播完是否自动进入聆听
  "timeout_ms": 10000       // 等待回答的超时（then_listen 时有效）
}
```

**MQTT Discovery 声明的实体**：
```yaml
sensor 小智状态        state_topic: .../state
sensor 小智最近识别    state_topic: .../stt
sensor 小智最近回复    state_topic: .../reply
button 小智开始聆听     command_topic: .../listen
button 小智停止        command_topic: .../stop
```

### 4.2 haimen ⇄ 设备（小智协议，不能自定义）

```
设备 → 服务器：发布到 publish_topic（在 OTA 里下发）
  消息类型：hello / listen / abort / mcp / goodbye
  音频：走 UDP，不走 MQTT

服务器 → 设备：服务器按约定主题发布
  消息类型：hello / stt / llm / tts / mcp / system / notify / alert
```

**topic 形式**：由设备的 `publish_topic` 决定（OTA 下发）；
服务器订阅设备的上行主题，向设备的下行主题发布。
具体命名需实测确认（可参考 `docs/mqtt-udp_zh.md` 与固件 `mqtt_protocol.cc`）。

## 五、实施步骤

### 里程碑 1：MQTT 客户端 + HA 侧打通（1-2 天，零风险）

```
① 新增 crates/haimen-xiaozhi/src/mqtt_client.rs
   · 用 rumqttc 连接 HA 的 broker
   · 配置项：endpoint / username / password / client_id 前缀
② 新增 crates/haimen-xiaozhi/src/ha_bridge.rs
   · MQTT Discovery：发布 sensor / button 配置
   · 订阅 haimen/xiaozhi/<id>/say|listen|stop
   · 发布 state / stt / reply
③ 配置：settings.toml 加 [xiaozhi.mqtt] 与 [xiaozhi.ha] 段
④ 验证：
   · HA 里出现"小智"设备与实体 ✅
   · 改 state topic 的值，HA 实体跟着变 ✅
   · 但这阶段设备还没接 MQTT，指令暂时无效（预期）
```

**产出**：HA 里能看到小智，但还不能真的驱动它。

### 里程碑 2：OTA 下发 MQTT 配置 + 设备连上 broker（1-2 天）

```
① ota.rs：当 protocol = "mqtt" 时，响应里加 mqtt 段
   {
     "mqtt": {
       "endpoint": "192.168.110.34:1883",
       "client_id": "<device_id>",
       "username": "vdr_runtime",
       "password": "vdr_runtime",
       "keepalive": 240
     },
     // 注意：是否还需要同时给 websocket 段？固件优先 MQTT，所以不必
   }
② 实测：设备重启 → 看 broker 是否收到设备 hello
③ 此时设备已切到 MQTT，但语音还没实现 → 暂时不能说话（预期）
```

**⚠️ 这一步之后，设备就不能用 WS 语音了** —— 直到里程碑 3 完成。
**建议**：在里程碑 2 之前把"回退到 websocket"的配置路径跑通并验证一次。

### 里程碑 3：UDP 音频通道 + 完整语音链路（3-4 天，核心）

```
① 新增 crates/haimen-xiaozhi/src/udp_audio.rs
   · hello 握手（transport: "udp"）→ 解析服务器 udp 配置
   · UDP socket 绑定与收发包
   · AES-CTR 加解密（aes + ctr crate）
   · 包结构编解码（type/flags/len/ssrc/timestamp/sequence）
   · 序列号管理（单调递增、乱序容错、防重放）
② 新增 crates/haimen-xiaozhi/src/mqtt_udp.rs（对应 ws.rs 的传输层）
   · 实现与 ws.rs 相同的会话状态机（Idle/Listening/Speaking/Notifying）
   · JSON 消息分发（hello/listen/abort/mcp/...）
   · 调用 strategy.rs 的现有管线
   · 音频入：UDP → protocol.rs 解码 → strategy
   · 音频出：strategy → protocol.rs 编码 → UDP 发送
   · 帧节奏：复用 ws.rs 里已验证的 next_send_at 累加逻辑
③ 验证：
   · 设备连上后能正常对话
   · 延迟与 WS 模式相当
```

### 里程碑 4：主动能力（2-3 天）

```
① notify 播报（HTTP 音频，不需要 UDP）
   · 新增 src/xiaozhi_notify.rs：文本 → TTS → Ogg Opus → 写到本地 HTTP 目录
   · 通过 MQTT 下发 notify 消息 { audio_url, subtitles }
   · haimen 内置一个静态文件服务（或复用现有 HTTP server 的 /notify 路由）
② tts 会话（问询模式）
   · 服务端主动发起：tts start → sentence_start → 音频帧(UDP) → tts stop
   · 设备播完自动进 Listening（固件已支持 ✅）
   · 等待回答：复用 haimen 的 no_speech_timeout_ms
③ HA 指令接线
   · haimen/xiaozhi/<id>/say → 播报
   · haimen/xiaozhi/<id>/listen → 直接开始听
④ 验证场景：
   · HA 自动化：温度 > 30 → say "客厅有点热，要开空调吗？" then_listen=true
   · 用户："开" → 执行 → 播报"好喔，开了"
```

## 六、风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| **切到 MQTT 后语音不可用** | 设备无法对话 | 里程碑 2 前先验证"改回 websocket"的回退路径；不要在里程碑 2 与 3 之间留太久 |
| **UDP 被网络拦截** | 音频完全不通 | 同在 192.168.110.x 子网，风险低；真机验证时先测 ping/UDP 连通 |
| **MQTT 主题命名猜错** | 收不到设备消息 | 里程碑 2 先只用 broker 抓包观察设备实际发布的主题 |
| **AES-CTR 实现细节错误** | 音频解不出来 | 严格按 docs/mqtt-udp_zh.md 的字段顺序与字节序 |
| **帧节奏在 UDP 下表现不同** | 语音卡顿 | 复用 WS 下已验证的 next_send_at 逻辑；必要时按 UDP 特性微调 |
| **HA broker 权限不足** | 无法发布 | `vdr_runtime` 已实测可发布 `homeassistant/...` ✅ |

### 回退方案

```
① settings.toml 里 [xiaozhi] protocol 改回 "websocket"
② 设备断电重启（它会重新走 OTA → 拿到 websocket 段）
③ 立即恢复现在的可用状态 ✅
```

**⚠️ 前提**：OTA 响应必须根据 `protocol` 配置决定下发哪一段，两套代码都要保留 ✅
