### 1.5 帧节奏控制：`PREBUFFER_COUNT` / `next_send_at` / `wait_until_send_slot`

这是整个传输层**最值钱、也最容易在 MQTT 版改坏**的部分。三个机制的分工：

#### ① `PREBUFFER_COUNT`（ws.rs:678，值 5）

只在流式路径生效。播放**开始前**先攒够 5 个 Audio 帧（Phase 1，ws.rs:727-783），
然后一次性连发（ws.rs:832-840），最后才进入 60ms 稳态。

- 作用：给 TTS 合成留 300ms 的 head start，避免"刚开始播就断供"。
- 直接代价：**用户说完 → 开始出声 +300ms 延迟**（注释 671-677 明确说了这个权衡）。
- 上限约束：预缓冲是**连发**的，超过固件 jitter buffer 容量会丢帧（表现为"半个字/语速压缩"）。
  所以注释里说 5 帧是实测取值，不能随意加大。
- 文本事件**不占**预缓冲名额：`Stt` 立即转发（ws.rs:733-738），`LlmSentence` 缓存到
  `pending_sentences` 等 `Tts::Start` 之后再 flush（ws.rs:739-741 / 822-827），
  避免助手文本先于设备进入 Speaking 态上屏。

#### ② `next_send_at`（ws.rs:847 初始化，903/958 累加）

```
预缓冲连发结束的时刻 ≈ T0
next_send_at = T0 + 60ms        // ws.rs:847

每发一帧：
  wait_until_send_slot(next_send_at)   // 等到绝对时刻
  socket.send(frame)
  next_send_at += 60ms                 // ws.rs:903，注意是「累加」不是「now+60」
```

**为什么必须累加而不是 `next_send_at = now + 60ms`**（注释 842-846）：
发送本身有耗时（几 ms）。若每次取 `now+60`，实际帧间隔 = `60 + 发送耗时`，
逐帧累积变慢，固件缓冲被慢慢耗尽 → 追帧跳帧，听感「开头正常、后面挤在一起」。

#### ③ `wait_until_send_slot`（ws.rs:1121-1159）

```rust
async fn wait_until_send_slot(
    socket: &mut WebSocket,
    next_send_at: &mut Instant,
) -> Option<PlaybackInterrupt> {
    loop {
        let now = Instant::now();
        snap_send_clock(next_send_at, now);      // 1127 落后 >60ms 则快进到 now
        let wait = next_send_at.saturating_duration_since(now);
        if wait.is_zero() { return None; }       // 1129-1131 到点，允许发
        ...
        tokio::select! {
            _ = &mut sleep => return None,       // 正常到点
            msg = socket.recv() => match msg {   // 期间收到设备消息
                ClientMessage::Abort => return Some(Abort),
                ClientMessage::Listen{state:Start,..} => return Some(ListenStart),
                _ => continue,                   // 其他消息忽略，继续等
            }
        }
    }
}
```

与批处理路径的 `wait_frame_interrupt`（ws.rs:1066）的关键差异：
后者每次调用都**重新起 60ms 计时**，socket 一有消息就提前返回 → 帧间隔被压缩 → 突发快发；
前者以 `next_send_at` **绝对时刻**对齐，socket 有消息时忽略、继续等。

#### ④ `snap_send_clock`（ws.rs:1104-1109）

断档（LLM 思考 / TTS 暂停）期间没有帧可发，`next_send_at` 会停留在很久以前。
恢复时若不修正，`wait==0` 会让积压帧**瞬间连发**，冲击 jitter buffer。
规则：落后 > 60ms（一帧）才快进到 `now`；落后 < 60ms 视为正常调度抖动，不动。

#### ⑤ 诊断：`record_frame_arrival_gap`（ws.rs:1169-1194）

记录相邻 Audio 帧**到达 frame_rx** 的间隔，> `FRAME_GAP_WARN_MS`(300ms, ws.rs:1162)
就 WARN 并累计。用途：区分「合成断供」（gap 大）与「发送节奏问题」（gap 正常）。
播放结束时汇总 `max_gap_ms` / `gap_warn_count`（ws.rs:987-1007）。
`specs/known-issues.md:30-33` 就是靠这个诊断排除了"断供"和"节奏"两个方向。

**完整数据流一图**：

```
TTS 合成（不定速，~7-8x 实时）
   │  mpsc::Sender<PlaybackEvent>  (容量 16, ws.rs:635)
   ▼
playback_frames_stream
   ├─ Phase1: 攒 5 帧 → 0ms 延迟
   ├─ Phase2: 连发 5 帧 ✅（设备缓冲 300ms）

              等待期间若 >60ms 无帧 → snap 修正

```

| PlaybackEvent | 传输层动作 | 消息 | ws.rs |
|---|---|---|---|

#### ⚠️ 复用性判断（与方案文档不一致，必须纠正）

`specs/mqtt-udp/实现方案.md:85` 把 `protocol.rs` 标为「传输无关 ✅ 可复用」。**这只对 WS 成立**：

- `Protocol2/3` 是 **WebSocket Binary 帧**的封装格式（16B / 4B 头，头里带 timestamp）。
- 小智 MQTT+UDP 的音频是**另一套封装**：`|type 1B|flags 1B|payload_len 2B|ssrc 4B|timestamp 4B|sequence 4B|payload|`，
  载荷是 **AES-CTR 加密的裸 Opus**（`实现方案.md:106-109`）。timestamp 在 UDP 头里，
  **不需要** `detect_and_parse` 去猜协议——传输层本来就知道是 Opus。

因此 MQTT 路径上：

| 函数 | 能否复用 | 说明 |
|---|---|---|
| `encode_protocol2` | ❌ 不能 | UDP 要自己的 16B 头 + AES；WS 的 16B 头字段语义完全不同 |
| `detect_and_parse` | ❌ 不能 | UDP 无需协议探测；timestamp 来自 UDP 头 |
| `AudioProtocol` / `ProtocolError` | ❌ 不需要 | 同上 |
| `is_valid_opus_data` | ✅ 逻辑可复用 | 建议改成 `pub(crate)`，用于校验解密后的 Opus TOC，当作 sanity check |
| `PROTOCOL3/RawOpus` 的**时间戳累加策略** | ✅ 思路可复用 | UDP 头没带 timestamp 时的兜底（防御性） |

**结论**：`protocol.rs` 在 MQTT 路径上几乎不需要改，也几乎用不到；新增的
`protocol_udp.rs` 才是那个位置上的对应物（§5.A）。这也意味着 **ws.rs 与 mqtt_udp.rs
的"编解码"部分不能共用**，只有状态机/节奏层能共用。

## 4. 协议选择点与配置

### 4.1 设备当前是怎么被判定为 WebSocket 连接的？

**服务端没有任何"判定"逻辑。** 真正的判定发生在设备固件里：

```c
// 小智固件 application.cc:544-559（引自 实现方案.md:35-41）
if (ota->HasMqttConfig())        → MqttProtocol      // MQTT 优先
else if (ota->HasWebsocketConfig()) → WebsocketProtocol
else                              → MqttProtocol
```

服务端这边的等价物只有两件事：

1. **OTA 响应内容**：`ota.rs:36-52` 恒发 `websocket` 段，从不发 `mqtt` 段 → 设备只能走 WS。
2. **WS 路由无条件挂载**：`lib.rs:33-39` 把 `/xiaozhi/ws` 挂上；
   `src/cli.rs:458-481`（`serve` 子命令）与 `src/gateway/mod.rs:187-192`（`start_all`）
   无条件构造策略并传给 `crate::web::start`，`src/web/mod.rs:123-137` 再挂路由。

也就是说：**"选择传输方式"目前完全没有抽象**，选 WS 是硬编码结果，不是配置。

### 4.2 开关最自然的注入点

推荐**三处改动 + 一个新增配置块**，全部在既有边界上，不引入新层：

### 5.1 共享状态机：怎么做、成本多大

**结论：可抽，且应该抽；边界极窄，成本约 0.5-1 天。**

理由：ws.rs 生产代码 1258 行里，**只有 3 个原语真正碰 WebSocket 类型**：

```rust
socket.send(Message::Text(...))      // ws.rs:1045  （send_json 内）
socket.send(Message::Binary(...))    // ws.rs:510/593/834/896/954
socket.recv()                        // ws.rs:82/167/208/1071/1136（主循环 + 等待槽 + 批处理等待）
```

其余约 850 行（预缓冲、发送时钟、drain、中断收尾、诊断、CancelGuard）**完全不知道 WebSocket 存在**。

**抽取方案**（`transport.rs`）：

```rust
/// 传输层 → 状态机的统一事件流（等价于 WS 的 Text/Binary/Close 三态）
pub enum TransportEvent {
    /// 控制消息（WS: Text 帧 / MQTT: 订阅到的 publish payload）
    Text(String),
    /// 音频帧（WS: Binary 帧 / UDP: 解密后的裸 Opus）
    Audio { timestamp: Option<u32>, data: Vec<u8> },
    /// 对端关闭（WS: Close/None/Err / MQTT: 设备离线或会话超时）
    Closed,
}

#[async_trait]
pub trait Transport: Send {
    /// 下发 JSON 控制消息
    async fn send_json(&mut self, msg: &ServerMessage) -> Result<(), ()>;
    /// 下发一帧音频（WS: encode_protocol2 + Binary；UDP: 加密封包）
    async fn send_audio(&mut self, frame: &AudioFrame) -> Result<(), ()>;
    /// 等下一个事件；None = 连接结束（语义等同 ws.rs 的 `socket.recv() -> None`）
    async fn recv_event(&mut self) -> Option<TransportEvent>;
}

/// 状态机入口（= 现在的 handle_ws_connection 去掉握手）
pub async fn run_session<T: Transport + ?Sized>(
    transport: &mut T,
    session: &mut Session,
) -> ();
```

- `Session`（ws.rs:26-37）、`SessionState`、所有 `playback_*`、`wait_*` 全部搬进 `transport.rs`，
  泛型参数 `T: Transport`。
- `ws.rs` 只剩 `WsTransport`（实现 3 个方法，约 100 行）+ `handle_ws_upgrade` + HELLO 握手
  （握手也可留在 ws.rs，用 `recv_event` 实现）。
- `mqtt_udp.rs` 只剩 `MqttUdpTransport`（实现 3 个方法 + 两路合并 select）。
- **额外收益**：`Transport` 可以写 `MockTransport`，把 ws.rs:1264-1616 那套"起真服务器 + 
  tungstenite"的集成测试换成纯内存测试，MQTT 版不依赖 broker 也能测状态机与节奏。

**成本拆解**：

| 步骤 | 工作量 | 风险 |
|---|---|---|
| 把 ws.rs 复制成 `transport.rs`，`socket` 参数替换为 `T: Transport` | 0.5 天 | 低（纯机械替换） |
| `ws.rs` 改成 `WsTransport` + 调 `run_session`，跑通 1264-1616 的现有测试 | 0.5 天 | 中（握手/状态迁移容易漏） |
| `MockTransport` + 把节奏测试改成无网络 | 0.25 天 | 低 |

**强烈建议的落地顺序（strangler 模式，避免"为了 MQTT 改坏正在跑的 WS"）**：

1. `cp ws.rs transport.rs`，把复制件泛型化 → **ws.rs 一行不动**，现有测试照跑。
2. 写 `mqtt_udp.rs` 对着 `transport.rs` 开发。
3. 等 MQTT 真机通了，再把 `ws.rs` 改成薄 `WsTransport` 并删掉重复状态机；
   `ws.rs:1356/1497` 两个测试此时是验收闸门（它们只打 `/xiaozhi/ws`，不该失败）。

若不做抽取（直接复制 900 行到 mqtt_udp.rs）：省 1 天，但之后每次调 60ms 节奏
（`PREBUFFER_COUNT`、`next_send_at` 累加、`snap_send_clock`）都要**双改**，且极大概率分叉——
`specs/known-issues.md:9-61` 的 KI-001 卡顿问题还没定位，节奏代码还要继续调。
**这笔帐不划算，建议抽。**

## 6. 风险与建议

1. **`protocol.rs` 的复用价值被高估（方案文档 §三.② 需修正）**
   WS 用 Protocol2/3 的 16B/4B 头；UDP 用 `type|flags|len|ssrc|timestamp|sequence` + AES。
   两者唯一的交集是"裸 Opus 载荷"。**不要**在 MQTT 路径上复用 `encode_protocol2`
   （`protocol.rs:110`）或 `detect_and_parse`（`protocol.rs:44`）；老老实实写 `protocol_udp.rs`。
   若照方案文档"protocol.rs 可复用"去做，会在真机联调第一天卡住。

2. **`docs/mqtt-udp_zh.md` 不存在**（方案文档 :95、:331、:446 都在引用它）。
   UDP 头字段顺序/字节序、AES-CTR 的 key/nonce 方向（上行与下行是否同一对）、
   timestamp 的单位（毫秒 vs 采样数）**全部无法从仓库确认**。
   - 特别注意 timestamp：WS 路径里策略按 **+60（毫秒）** 递增
     （`src/xiaozhi_asr_llm_tts.rs:2551-2557`、`:2741-2747`、`:3224-3234`）。
     UDP 头的 timestamp 在固件侧通常是**采样数**语义。**不要直接把 `frame.timestamp` 写进 UDP 头**，
     在 `udp_audio::send_opus` 里做一次显式换算（`samples = ms * sample_rate / 1000`），
     并把换算做成常量便于真机调参。
   - 建议第一个交付物就是 `device_sim.py`（`实现方案.md:430` 也这么要求），
     在真机切换前把协议钉死。

3. **OTA 一旦下发 `mqtt` 段，设备就切过去了，且没有运行时回退**
   （固件逻辑 `实现方案.md:35-41`，无 fallback）。回退只能改 `protocol = "websocket"`
   + 设备断电重启。因此：
   - 默认值必须是 `"websocket"`；
   - `OtaResponse.mqtt` 必须是 `Option` 且 `skip_serializing_if = "Option::is_none"`；
   - 切换前先用模拟器把 M2'/M3' 全链路跑通（`实现方案.md:396-405` 已采用这个顺序）。

4. **MQTT `client_id` 冲突会导致设备互踢**
   两台设备若用同一 `client_id` 连 broker，broker 会踢掉前一个。
   - OTA 下发给设备的 `client_id` 必须按设备唯一（用 `body.mac_address`，见 `types.rs:168`）。
   - 服务端自己连 broker 的 `client_id` 要用 `client_id_prefix + 随机后缀`，**不能**用设备 MAC，
     否则会与设备那条连接同名互踢。
   - `实现方案.md:388` 的"client_id 用设备 MAC"是 **M1 HA 桥接**（haimen 替每台设备各开一条
     连接）的约定，与"设备自己连 broker"是两条不同的连接，别混用同一个 id。

5. **`handle_ota` 现在把请求体丢了**
   `ota.rs:17` 是 `Json(_body)`，只校验了 `Device-Id` 头。MQTT 段需要 MAC 生成 `client_id`，
   所以必须改成 `Json(body)` 并读 `body.mac_address`。这是个小改动，但漏了会拿到全 `"unknown"`
   的 client_id，一上两台设备就互踢。

6. **UDP 通告地址不能用 `0.0.0.0`**
   设备会拿这个地址回包。必须用 `local_ip_address::local_ip()` 探测局域网 IP
   （依赖已在 `crates/haimen-xiaozhi/Cargo.toml:20`）。
   `实现方案.md:444` 也明确点了这个坑。

7. **`send_json` 的失败语义变了**
   WS 的 `socket.send()` 失败 = 对端已断，可以立即中止回放（`ws.rs:510/834/896`）。
   MQTT 的 `publish().await` 成功只代表**入队到 rumqttc**；真正的失败要靠 `EventLoop`
   的 `Err` 或 QoS1 的 `PubAck` 超时。若直接把 `send_json` 映射成 `publish().await`，
   会出现"设备早掉线、服务器还在欢快播音频"（UDP 是盲发，不会有错误）。
   建议：UDP 侧用 `send_to` 的 `Err` 作为断线信号，MQTT 侧单独维护 last-seen 心跳。

8. **多设备会话隔离是新增复杂度，WS 版没有**
   WS 是"一连接一 task"，`Session` 天然隔离。MQTT 一个连接 N 台设备，需要：
   `HashMap<device_id, mpsc::Sender<TransportEvent>>` 路由表；
   每台设备独立 UDP 端口或独立 ssrc（同一端口也可，用 `peer` 区分，但 NAT 下建议独立端口）；
   设备离线（MQTT LWT / keepalive 超时）时要 drop 会话并 `CancelGuard` 取消未完成的
   ASR/LLM/TTS（复用 `transport.rs` 的取消守卫）。

9. **`session_id` 的语义要重新定义**
   WS 每连接一个 UUID（`ws.rs:92`），MQTT 是长连接。建议每轮对话（`listen/start`）
   重建 `session_id`，否则单设备多轮对话在日志里无法区分。
   注意 `strategy` 侧用 `session_id` 做日志关联（如 `xiaozhi_asr_llm_tts.rs:1565`），
   重建不影响正确性。

10. **KI-001 卡顿问题未定论，节奏代码还会继续调**
    `specs/known-issues.md:9-61` 记录了"语音卡顿"待排查，其中预缓冲帧数、发送节奏都是
    可疑项。这意味着 `playback_frames_stream` 还会被改。**这是"必须抽公共层"的最强理由**——
    否则每调一次参数都要改两处，且真机对比实验（WS vs MQTT）会因为两处实现分叉而失效。

11. **建议的实施顺序（与 `实现方案.md:396-405` 的 M2'/M3' 对齐）**

    ```
    ① transport.rs 抽取（ws.rs 先不动），现有测试全绿          0.5-1 天
    ② protocol_udp.rs + 单测（头部/AES/重放）                   0.5 天
    ③ udp_audio.rs + device_sim.py 打通 UDP 握手与收发          1 天
    ④ mqtt.rs + mqtt_udp.rs（会话层），模拟器跑通 hello→对话    1 天
    ⑤ 根 crate 配置 + OTA mqtt 段（默认仍 websocket）            0.5 天
    ⑥ 真机切换（改 protocol + 重启），对比延迟与 KI-001          0.5 天
    ```

12. **不要动的东西**
    - `strategy.rs`：12 个方法的契约已经够用，MQTT 不需要新钩子（`wake_greeting` /
      `goodbye_frames` 都是"返回 Vec<AudioFrame>"，与传输无关）。
    - `EchoStrategy` / `TtsStrategy` / `AsrTtsStrategy`：完全复用。
    - `AsrLlmTtsStrategy`（`src/xiaozhi_asr_llm_tts.rs`，4908 行）：一行都不用改。
      它只依赖 `AudioFrame` / `PlaybackEvent` / `Notify`，与传输无关。
    - `protocol.rs`：一行都不用改（见风险 1）。
