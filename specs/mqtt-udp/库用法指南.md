## 0. 先看结论（TL;DR）

1. **`EventLoop` 必须放进独立 tokio task 里持续 `poll().await`**。没人 poll 时，`AsyncClient` 的 `publish/subscribe` 只是把请求塞进一个容量为 `cap` 的 channel：塞满之后 `publish().await` 永久挂起，`try_publish()` 返回错误，连接永远不会建立。
2. `AsyncClient::new(options, cap)` 的第二个参数是**请求 channel 容量**，不是连接数。实时音频场景建议 `cap >= 32`；不要用 0。
3. 0.24 的 builder 方法是 **`set_keep_alive` / `set_credentials` / `set_clean_session`**，返回 `&mut Self`，不是 `with_*`。**不能**把链式调用结果直接传给按值接收 `MqttOptions` 的 `AsyncClient::new`（会得到 `expected MqttOptions, found &mut MqttOptions`）。
4. `publish().await` 的语义是“请求已进入 EventLoop 的 channel”，**不是**“已写进 socket”，更不是“broker 已 ack”。要确认 QoS1/2 送达，需要跟踪 `Outgoing::Publish(pkid)` 与 `Incoming::PubAck/PubComp(pkid)`。
5. AES-CTR 用 `ctr::Ctr128BE<aes::Aes128>`（16 字节 IV）或 `Ctr128BE<Aes256>`（32 字节 key + 16 字节 IV）。加解密是同一个 `apply_keystream`，**无 padding、长度不变**。
6. **小智 UDP 协议的关键事实：16 字节包头就是 AES-CTR 的 IV。** 不是用 hello 里那个静态 `nonce` 一直加密整条流；固件会把 `payload_len/timestamp/sequence` 写进 nonce 模板，再用整个 16 字节包头作为 IV。详见 2.3 与 [固件源码](https://github.com/78/xiaozhi-esp32/blob/main/main/protocols/mqtt_protocol.cc)。
7. 120 字节 / 60ms 的音频帧做 AES-CTR 是微秒级开销，**不需要 `spawn_blocking`**；真正危险的是在音频循环里 `await` 一个可能被背压卡住的 MQTT `publish()`。音频循环里优先用 `try_publish()` + 有界 channel + 丢帧策略。
8. 单 UDP socket 可以同时收发（`recv_from`/`send_to` 都只借 `&self`）：用 `Arc<UdpSocket>`，一个 recv task 收，多个 task 调 `send_to`。多设备用 **源地址 + 包头 ssrc** 联合区分，ssrc 作为稳定主键、源地址作为回包地址。

## 1. rumqttc 0.24

### 1.1 客户端创建

精确签名（来自 0.24.0 源码 `src/client.rs`）：

```rust
pub fn new(options: MqttOptions, cap: usize) -> (AsyncClient, EventLoop)
```

- `options`：连接参数，按值传入。
- `cap`：`AsyncClient` → `EventLoop` 的**有界请求 channel 容量**（publish/subscribe/ack/disconnect 都走它）。
- 返回 `AsyncClient`（可 `Clone`，内部只有一个 channel `Sender`）和 `EventLoop`（**不可 Clone**，独占网络连接、inflight 状态、keepalive 定时器）。

最小创建：

```rust
use std::time::Duration;
use rumqttc::{AsyncClient, MqttOptions};

let mut options = MqttOptions::new(
    "haimen-device-aa:bb:cc:dd:ee:ff", // client_id
    "192.168.110.34",                  // host
    1883,                              // port
);
options
    .set_keep_alive(Duration::from_secs(240))
    .set_clean_session(true)
    .set_credentials("vdr_runtime", "vdr_runtime");

let (client, eventloop) = AsyncClient::new(options, 64);
```

✅ 上面这种“先 `let mut options`，再链式 `set_*`”是 0.24 的正确写法。下面这种**编译不过**：

```rust
// ❌ E0308: expected `MqttOptions`, found `&mut MqttOptions`
let (client, eventloop) = AsyncClient::new(
    MqttOptions::new("id", "localhost", 1883)
        .set_keep_alive(Duration::from_secs(30)),
    64,
);
```

#### MqttOptions builder 一览（0.24 的确切方法名）

| 需求 | API | 备注 |
|---|---|---|
| client_id / host / port | `MqttOptions::new(id, host, port)` | 没有单独的 `set_client_id`；id 在构造时给 |
| username / password | `set_credentials(username, password) -> &mut Self` | 只支持用户名密码；证书走 TLS transport |
| keepalive | `set_keep_alive(Duration) -> &mut Self` | 默认 60s；`Duration::ZERO` 表示关闭；**0 < d < 1s 会 panic**；内部按 `as_secs() as u16` 截断 |
| clean session | `set_clean_session(bool) -> &mut Self` | 默认 `true`；`false` + 空 client_id 会 panic |
| 遗嘱 | `set_last_will(LastWill) -> &mut Self` | `LastWill::new(topic, payload, qos, retain)` |
| 最大包长 | `set_max_packet_size(incoming, outgoing) -> &mut Self` | 默认各 10 KiB；超 outgoing 会导致 eventloop 报 `OutgoingPacketTooLarge` |
| inflight 上限 | `set_inflight(u16) -> &mut Self` | 默认 100；0 会 panic；限制 QoS1/2 未 ack 的并发数 |
| 手动 ack | `set_manual_acks(bool) -> &mut Self` | 默认 false；true 时 QoS1/2 必须自己 `client.ack(&p).await` |
| 重传节流 | `set_pending_throttle(Duration) -> &mut Self` | 默认 0；重连后重传 pending 包的最小间隔 |
| TLS / WebSocket | `set_transport(Transport) -> &mut Self` | 默认 `Transport::Tcp`；`rumqttc` 默认 feature 含 `use-rustls` |
| 同步 Client 的 channel 容量 | `set_request_channel_capacity(usize)` | **只影响 `rumqttc::Client`（同步版）**；异步版用 `AsyncClient::new` 的 `cap` |

`MqttOptions` 实现了 `Clone`，但 `AsyncClient::new` 要的是所有权；需要保留一份配置时先 `clone()`。

TLS 示例（默认 feature 已启用 rustls）：

```rust
use rumqttc::{MqttOptions, Transport};

let mut options = MqttOptions::new("id", "mqtt.example.com", 8883);
options.set_transport(Transport::tls_with_default_config());
// 自定义 CA / 客户端证书：
// options.set_transport(Transport::tls(ca_pem, Some((cert_pem, key_pem)), None));
```

> ⚠️ 需验证：目标 broker 的证书链、SNI、客户端证书要求。局域网 Mosquitto 一般 1883 明文，不涉及此路径。

#### `AsyncClient` 常用方法签名

```rust
impl AsyncClient {
    pub async fn publish<S, V>(
        &self, topic: S, qos: QoS, retain: bool, payload: V,
    ) -> Result<(), ClientError>
    where S: Into<String>, V: Into<Vec<u8>>;

    pub fn try_publish<S, V>(
        &self, topic: S, qos: QoS, retain: bool, payload: V,
    ) -> Result<(), ClientError>
    where S: Into<String>, V: Into<Vec<u8>>;

    pub async fn subscribe<S: Into<String>>(
        &self, topic: S, qos: QoS,
    ) -> Result<(), ClientError>;

    pub async fn subscribe_many<T>(&self, topics: T) -> Result<(), ClientError>
    where T: IntoIterator<Item = SubscribeFilter>;

    pub async fn unsubscribe<S: Into<String>>(&self, topic: S) -> Result<(), ClientError>;

    pub async fn disconnect(&self) -> Result<(), ClientError>;

    pub async fn ack(&self, publish: &Publish) -> Result<(), ClientError>;

```

`AsyncClient` 是 `Clone` 的；clone 出来的句柄共享同一个 EventLoop 请求 channel。

### 1.2 EventLoop 驱动

精确签名：

```rust
pub async fn poll(&mut self) -> Result<Event, ConnectionError>
```

`Event` 与相关类型：

```rust
pub enum Event {
    Incoming(Incoming), // Incoming = Packet
    Outgoing(Outgoing),
}

pub enum Outgoing {
    Publish(u16),   // QoS0 的 pkid 为 0
    Subscribe(u16),
    Unsubscribe(u16),
    PubAck(u16), PubRec(u16), PubRel(u16), PubComp(u16),
    PingReq, PingResp, Disconnect,
    AwaitAck(u16),
}

pub enum Packet {
    Connect(Connect), ConnAck(ConnAck), Publish(Publish),
    PubAck(PubAck), PubRec(PubRec), PubRel(PubRel), PubComp(PubComp),
    Subscribe(Subscribe), SubAck(SubAck),
    Unsubscribe(Unsubscribe), UnsubAck(UnsubAck),
    PingReq, PingResp, Disconnect,
}
```

`poll()` 的行为：

1. 第一次调用时建立 TCP/TLS 连接、发 CONNECT、等 CONNACK；**成功时返回 `Event::Incoming(Packet::ConnAck(..))`**。
2. 之后每次调用等待“下一个事件”：网络来包、用户请求、keepalive 到点。
3. 连接断开/出错时返回 `Err(ConnectionError)`，内部把 `network` 清空；**下一次 `poll()` 会自动重连**。
4. 重连**没有内置退避**；`Err` 之后睡多久由调用方决定。
5. `poll()` 不是忙轮询；它内部 `select!` 在 socket / 请求 channel / keepalive 定时器上等待。

关于“`poll()` 阻塞怎么办”：

- `poll().await` 的“阻塞”是 **async 挂起**，不占用 OS 线程；它挂起时 tokio 可以去跑别的 task，这是正常状态，不需要 timeout。
- 它同时 select 了请求 channel，所以即使网络没消息，别的 task 调 `publish()/subscribe()` 也会把它唤醒。
- 真正的问题是：**poll 所在 task 被同步阻塞代码卡住**（文件 IO、`std::thread::sleep`、CPU 密集循环），或者 poll task 根本没被 spawn。此时请求 channel 会堆满，`publish().await` 挂起，`try_publish()` 失败。
- 背压的容量就是 `AsyncClient::new(options, cap)` 的 `cap`；不要把它设得比“你能容忍的积压”还大。实时场景宁可 `try_publish` 失败丢帧，也不要无限积压。
- **不要把 `EventLoop` 放进 `Arc<Mutex<...>>` 让多个 task 抢着 poll**：`poll()` 要 `&mut self` 且会长时间 await，持锁跨 await 会直接死锁/串行化。正确做法是“一个 task 独占 EventLoop，其他 task 只持有 `AsyncClient`”。

#### 标准驱动方式：独立 tokio task

```rust
use std::time::Duration;
use rumqttc::{AsyncClient, Event, Outgoing, Packet, QoS};
use tokio::time;

async fn run_eventloop(mut eventloop: rumqttc::EventLoop, client: AsyncClient) {
    let mut backoff = Duration::from_secs(1);

    loop {
        match eventloop.poll().await {
            Ok(Event::Incoming(Packet::ConnAck(ack))) => {
                backoff = Duration::from_secs(1); // 连上了，重置退避
                println!("mqtt connected, session_present={}", ack.session_present);

                // 每次（重）连接都重新订阅；clean_session=true 时 broker 不保留订阅。
                if let Err(e) = client.subscribe("haimen/xiaozhi/+/up", QoS::AtLeastOnce).await {
                    eprintln!("subscribe failed: {e}");
                }
            }
            Ok(Event::Incoming(Packet::SubAck(ack))) => {
                println!("subacked pkid={} codes={:?}", ack.pkid, ack.return_codes);
            }
            Ok(Event::Incoming(Packet::Publish(p))) => {
                // 默认 manual_acks=false，QoS1/2 的 ack 已由 rumqttc 自动发出。
                // 这里不要做重活；转给 mpsc / spawn 出去。
                println!("recv {} bytes on {}", p.payload.len(), p.topic);
            }
            Ok(Event::Outgoing(Outgoing::Disconnect)) => {
                println!("disconnect packet sent");
                break; // 优雅关闭完成
            }
            Ok(_) => {}
            Err(e) => {
                // 认证失败 / client_id 冲突等属于“重试也没用”的错误，见 1.4。
                eprintln!("eventloop error: {e}; reconnect in {:?}", backoff);
                time::sleep(backoff).await;
                backoff = (backoff * 2).min(Duration::from_secs(30));
            }
        }
    }
}
```

启动：

```rust
let (client, eventloop) = AsyncClient::new(options, 64);
let mut poller = tokio::spawn(run_eventloop(eventloop, client.clone()));
```

#### 优雅关闭

```rust
// 1) 先把 pending 的 QoS 消息尽量发完（严格做法：等对应 PubAck/PubComp）
time::sleep(Duration::from_millis(200)).await;

// 2) 发 DISCONNECT 请求
client.disconnect().await?;

// 3) 等 EventLoop 处理完 Disconnect 请求并退出
match time::timeout(Duration::from_secs(3), &mut poller).await {
    Ok(Ok(())) => { /* clean */ }
    Ok(Err(e)) => eprintln!("poller join error: {e}"),
    Err(_) => {
        eprintln!("disconnect timeout, aborting poller");
        poller.abort();
    }
}
```

注意：

- `client.disconnect().await` 只是把 `Request::Disconnect` 放进 channel；**不等待网络写出**。`EventLoop` 处理该请求时会 push `Outgoing::Disconnect` 事件，循环收到后 break 即可。
- 不要用 `select!` 去“取消” `eventloop.poll()` 来实现关机。取消一个正在进行的 poll 可能把它留在半读/半写状态，`poll` 没有文档保证 cancel-safe。**正确做法是发 DISCONNECT，让 poll 自己返回。**
- 如果 poll 卡在网络上、连 DISCONNECT 都发不出去，用 `JoinHandle::abort()` 兜底（进程退出前调用）。

#### 没人 poll 会发生什么

`AsyncClient::new` **不会建立连接**，只是建了 channel。没有 poll：

- CONNECT 永远不发，订阅永远不会生效；
- `publish().await` 在 channel 有空间时立即返回（看起来“成功”），但消息永远不出网；
- channel 塞满（`cap` 个请求）后，`publish().await` / `subscribe().await` **永久挂起**；
- `try_publish()` 返回 `ClientError::TryRequest(..)`（内部是 `TrySendError::Full`）；
- 没有 keepalive/PingReq，即使之前连上过也会被 broker 断开；
- broker 下来的消息堆在 OS 接收缓冲区，最终触发 TCP 背压，broker 可能断开或丢消息。

**这是 rumqttc 最常见的生产事故。**

### 1.3 订阅与发布

#### 订阅

```rust
// 单主题
client.subscribe("haimen/xiaozhi/+/up", QoS::AtLeastOnce).await?;

// 多主题
use rumqttc::SubscribeFilter;
client.subscribe_many([
    SubscribeFilter::new("haimen/xiaozhi/+/up".to_string(), QoS::AtLeastOnce),
    SubscribeFilter::new("haimen/xiaozhi/+/state".to_string(), QoS::AtMostOnce),
]).await?;

// 取消订阅
client.unsubscribe("haimen/xiaozhi/+/up").await?;
```

`SubscribeFilter` 定义：

```rust
pub struct SubscribeFilter {
    pub path: String,
    pub qos: QoS,
}
impl SubscribeFilter {
    pub fn new(path: String, qos: QoS) -> SubscribeFilter;
}
```

订阅结果通过 `Event::Incoming(Packet::SubAck(SubAck))` 返回：

```rust
pub struct SubAck {
    pub pkid: u16,
    pub return_codes: Vec<SubscribeReasonCode>,
}
pub enum SubscribeReasonCode {
    Success(QoS), // broker 实际授予的 QoS，可能低于请求值
    Failure,
}
```

> 订阅主题支持 `+` / `#` 通配符；`publish` 的主题**不能**含通配符，否则 rumqttc 直接返回 `ClientError::Request(..)`（本地校验，不会发出去）。

#### 发布与 QoS 差异

三个 QoS 的 **API 完全一样**，区别只在协议行为与延迟：

```rust
client.publish("topic", QoS::AtMostOnce, false, b"payload").await?;
client.publish("topic", QoS::AtLeastOnce, false, b"payload").await?;
client.publish("topic", QoS::ExactlyOnce, false, b"payload").await?;
```

| QoS | 协议交互 | pkid | 延迟/开销 | 语义 | 适用 |
|---|---|---|---|---|---|
| 0 | 只有 PUBLISH | 无（0） | 最低 | 最多一次，可能丢 | 实时音频、状态刷新 |
| 1 | PUBLISH → PUBACK | 有 | +1 RTT | 至少一次，可能重复 | 控制指令、事件 |
| 2 | PUBLISH → PUBREC → PUBREL → PUBCOMP | 有 | +2 RTT | 恰好一次（broker 侧） | 计费、不可重复操作 |

关键点：

1. **`publish().await` 只保证“请求入队”**，不保证发出、更不保证 ack。
2. `publish()` 的 `payload` 是 `V: Into<Vec<u8>>`，二进制安全；可以直接传 `Vec<u8>`、`&[u8]`、`b"..."`。
3. QoS1/2 的完成事件：
   - 发送侧：先看到 `Event::Outgoing(Outgoing::Publish(pkid))`；
   - QoS1：再看到 `Event::Incoming(Packet::PubAck(puback))` 且 `puback.pkid == pkid`；
   - QoS2：再看到 `Incoming(Packet::PubRec/PubRel/PubComp)`，最终是 `PubComp`。
   - **没有 `publish_and_wait_ack()` 这种 API**。要严格确认，需要自己维护 `pkid -> oneshot::Sender` 表。
4. `Outgoing::AwaitAck(pkid)` 是 rumqttc 内部流控信号，不是“业务 ack”。
5. `retain = true` 会让 broker 保留最后一条消息；订阅时立刻收到 retained 消息。清理 retained 用空 payload + retain=true。
6. 协议层不保证 QoS2 的“端到端恰好一次”到你的业务处理；broker 侧是恰好一次，应用侧仍可能因重连/重复投递看到重复，业务要幂等。

#### 接收与 ack

```rust
Ok(Event::Incoming(Packet::Publish(p))) => {
    // p.topic: String
    // p.payload: bytes::Bytes（可用 &p.payload[..] / p.payload.to_vec()）
    // p.qos: QoS, p.retain: bool, p.dup: bool, p.pkid: u16
    handle(&p.topic, &p.payload);
}
```

默认 `manual_acks = false`：

- QoS1 收到 PUBLISH 后自动回 PUBACK；
- QoS2 收到 PUBLISH 后自动回 PUBREC，收到 PUBREL 后自动回 PUBCOMP。

如果设置 `manual_acks(true)`，必须自己 ack：

```rust
Ok(Event::Incoming(Packet::Publish(p))) => {
    // 先持久化/入队，成功后再 ack；否则进程崩溃会丢消息
    persist_or_enqueue(&p).await?;
    client.ack(&p).await?;
}
```

> `ack()` 对 QoS0 是空操作；对 QoS1 发 PUBACK；对 QoS2 发 PUBREC。之后 broker 的 PUBREL 到达时，rumqttc 会自动回 PUBCOMP（这一步不需要业务再 ack）。

#### 背压与 `try_publish`

| 调用 | 行为 | 适用 |
|---|---|---|
| `publish().await` | channel 满时挂起等待；EventLoop 停止时返回错误 | 控制面、允许背压 |
| `try_publish()` | 立即返回；满/断连都返回 `Err(ClientError::TryRequest(..))` | 实时循环、不允许挂起 |
| `publish_bytes()` | 同 `publish`，但接受 `bytes::Bytes`（避免一次拷贝） | 已有 `Bytes` 时 |

`ClientError` 只有两个变体：

```rust
pub enum ClientError {
    Request(Request),     // publish/subscribe 等 async 发送失败（channel 关闭）
    TryRequest(Request),  // try_* 发送失败（满或关闭）
}
```

它**不区分** Full 和 Disconnected。实时场景只能“失败就丢/记指标”，不要重试到阻塞。

### 1.4 重连与错误处理

`ConnectionError`（0.24）主要变体：

```rust
pub enum ConnectionError {
    MqttState(StateError),
    NetworkTimeout,
    FlushTimeout,
    Io(std::io::Error),
    ConnectionRefused(ConnectReturnCode),
    NotConnAck(Packet),
    RequestsDone,
    // feature 相关：Websocket(..), Tls(..), Proxy(..), ...
}
```

`ConnectReturnCode`：

```rust
pub enum ConnectReturnCode {
    Success = 0,
    RefusedProtocolVersion,
    BadClientId,
    ServiceUnavailable,
    BadUserNamePassword,
    NotAuthorized,
}
```

处理策略：

| 错误 | 含义 | 建议 |
|---|---|---|
| `Io(_)` | TCP 断开、RST、DNS 临时失败 | 退避重连 |
| `NetworkTimeout` | 连接超时（默认 5s） | 退避重连 |
| `FlushTimeout` | 写 socket 超时 | 退避重连 |
| `MqttState(AwaitPingResp)` | keepalive ping 没回 | 退避重连 |
| `ConnectionRefused(BadUserNamePassword / NotAuthorized / BadClientId)` | 认证/ID 问题 | **不要无限重试**；告警/修配置 |
| `ConnectionRefused(ServiceUnavailable / RefusedProtocolVersion)` | broker 暂不可用/协议不符 | 退避重试；协议不符要修版本 |
| `NotConnAck(_)` | 连上后收到非 CONNACK | 视为致命，记录包 |
| `RequestsDone` | 所有 `AsyncClient` 句柄都已 drop，请求 channel 关闭 | 正常退出循环 |

#### 重连循环的推荐写法

```rust
use rumqttc::{ConnectionError, ConnectReturnCode};

async fn drive(mut eventloop: rumqttc::EventLoop, client: AsyncClient) {
    let mut backoff = Duration::from_secs(1);
    loop {
        match eventloop.poll().await {
            Ok(Event::Incoming(Packet::ConnAck(ack))) => {
                backoff = Duration::from_secs(1);
                // 无论 session_present 是 true/false，都重新订阅最稳妥（订阅是幂等的）
                let _ = client.subscribe("haimen/xiaozhi/+/up", QoS::AtLeastOnce).await;
                let _ = ack;
            }
            Ok(Event::Outgoing(Outgoing::Disconnect)) => break,
            Ok(_) => {}
            Err(ConnectionError::ConnectionRefused(
                ConnectReturnCode::BadUserNamePassword
                | ConnectReturnCode::NotAuthorized
                | ConnectReturnCode::BadClientId,
            )) => {
                eprintln!("mqtt auth/client-id fatal, stop reconnecting");
                break;
            }
            Err(ConnectionError::RequestsDone) => break,
            Err(e) => {
                eprintln!("mqtt error: {e}; retry in {:?}", backoff);
                tokio::time::sleep(backoff).await;
                backoff = (backoff * 2).min(Duration::from_secs(30));
            }
        }
    }
}
```

#### ConnAck 与 session_present

```rust
pub struct ConnAck {
    pub session_present: bool,
    pub code: ConnectReturnCode,
}
```

- `clean_session = true`：每次连接都是新会话，broker 不保留订阅和离线 QoS 消息。**必须在每次 ConnAck 后重新 subscribe。**
- `clean_session = false` + 相同 client_id：broker 保留会话；`session_present == true` 时订阅通常还在。但为了代码简单、行为确定，建议**每次 ConnAck 都重新订阅**（幂等），不要依赖 `session_present`。
- `clean_session = false` 时本地也会保留 pending QoS 消息用于重传；`AsyncClient::new` 的 `cap` 建议设小一点（官方 `clean()` 注释甚至建议 0，但 0 对 `try_publish` 极不友好；生产建议 16–64）。

#### keepalive

```rust
options.set_keep_alive(Duration::from_secs(240)); // 小智协议默认 240s
```

- EventLoop 自动在空闲时发 PINGREQ，并校验 PINGRESP；不需要业务层管。
- keepalive 过短 + 网络抖动会造成频繁重连；过长则半开连接发现慢。
- 协议里 `keep_alive` 是 `u16` 秒；超过 65535s 会被截断。

#### 重复 client_id

同一个 client_id 建立第二条连接时，Mosquitto 默认会踢掉旧连接。结果是两边反复重连、互相踢。**每个设备/每个 haimen 实例必须用唯一 client_id**（小智方案里用设备 MAC）。

#### 修改配置后重连

`EventLoop` 的 `mqtt_options` 是 `pub` 字段：

```rust
// 例如收到认证失败后，更新密码再 poll（不常见，但 API 允许）
eventloop.mqtt_options.set_credentials("user", "new-password");
```

修改后下一次 `poll()` 会用新配置重连。不要在 `poll()` 进行中从别的 task 改它（没有同步保护）。

### 1.5 常见坑

1. **EventLoop 没人 poll**：见 1.2。表现是“publish 返回 Ok 但 broker 收不到”“subscribe 永远没 SubAck”“跑一段时间后 publish 卡死”。
2. **`publish().await` 卡住音频循环**：channel 满或 EventLoop 卡住时，await 会挂起。实时循环用 `try_publish()` 或“专用网络 task + mpsc”。
3. **cap 太小 / 为 0**：`cap = 0` 是 rendezvous channel，`try_publish` 几乎总是失败；`publish().await` 要等 EventLoop 正好在收。建议 32–128。
4. **builder 链式结果直接传 `AsyncClient::new`**：`&mut MqttOptions` ≠ `MqttOptions`。先 `let mut options`，设置完再传。
5. **clean_session=true 却不重订阅**：断线重连后收不到消息。每次 ConnAck 都 subscribe。
6. **在 `select!` 里取消 `poll()`**：没有 cancel-safe 保证。用 `disconnect()` + 超时 + `abort()` 兜底。
7. **在 poll 循环里做重活**：比如同步文件 IO、CPU 密集处理、`std::thread::sleep`。EventLoop 停转 → 所有 publish/subscribe 背压 → keepalive 超时。把活丢给 `mpsc`/`spawn`。
8. **把 `publish().await` 当成“已送达”**：它只代表入队。QoS0 甚至不保证出网。
9. **超过 `max_packet_size`**：默认 10 KiB；大 JSON/音频包会触发 `StateError::OutgoingPacketTooLarge`，而且是在 poll 里报错，表现为“莫名断线”。发布大包前 `set_max_packet_size(in, out)`。
10. **重复 client_id**：互相踢，日志里看到频繁 ConnAck/断开。
11. **poller task panic 后没人发现**：`AsyncClient` 还在，调用会返回 channel closed 错误，但业务可能忽略。监控 `JoinHandle`，或在 poll 循环里 catch 所有错误继续。
12. **以为 QoS2 就是端到端 exactly-once**：broker 侧是；你的业务处理仍要做幂等。
13. **MQTT 3.1.1 vs 5.0**：`rumqttc` 根路径是 3.1.1（`Packet`/`MqttOptions`/`AsyncClient`）；MQTT5 在 `rumqttc::v5::*`，API 不同，不要混用。
14. **TLS 端口/feature**：`rumqttc` 默认 feature 是 `use-rustls`；`Transport::tls_with_default_config()` 用系统根证书。局域网 1883 明文不需要。
15. **broker 主动断开时不一定有 `Packet::Disconnect`**：MQTT 3.1.1 broker 通常直接关 TCP，你收到的是 `Err(Io)`。不要只依赖 `Incoming(Disconnect)` 做重连。

### 1.6 最小可运行示例（完整代码）

> ✅ 已验证：编译通过；并用第 5 节的进程内 mock broker 跑通了“连接 → 订阅 → 收消息 → 发消息 → DISCONNECT”全流程。
> 运行前需要一个 MQTT broker（例如 `mosquitto -p 1883`），把 host/port/credentials 换成你的。

```rust
// src/bin/mqtt_min.rs
use std::time::Duration;

use rumqttc::{AsyncClient, Event, MqttOptions, Outgoing, Packet, QoS};
use tokio::time;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // 1. 连接参数。0.24 的 builder 方法都叫 set_*，返回 &mut Self。
    let mut options = MqttOptions::new("haimen-audio-demo", "127.0.0.1", 1883);
    options
        .set_keep_alive(Duration::from_secs(30))
        .set_clean_session(true)
        .set_credentials("haimen", "secret");

    // 2. AsyncClient 可 Clone；EventLoop 必须独占并持续 poll。
    let (client, mut eventloop) = AsyncClient::new(options, 64);
    let poller_client = client.clone();
    let publisher = client;

    // 3. EventLoop 放到独立 tokio task，负责网络 I/O、keepalive、重连。
    let mut poller = tokio::spawn(async move {
        loop {
            match eventloop.poll().await {
                Ok(Event::Incoming(Packet::ConnAck(ack))) => {
                    println!("connected: session_present={}", ack.session_present);
                    // clean_session=true 时 broker 不保留订阅，每次连接都重订阅。
                    if let Err(e) = poller_client
                        .subscribe("haimen/demo/#", QoS::AtLeastOnce)
                        .await
                    {
                        eprintln!("subscribe failed: {e}");
                    }
                }
                Ok(Event::Incoming(Packet::SubAck(ack))) => {
                    println!("subacked: pkid={} codes={:?}", ack.pkid, ack.return_codes);
                }
                Ok(Event::Incoming(Packet::Publish(p))) => {
                    // 默认 manual_acks=false，QoS1/2 的 ack 由 rumqttc 自动发送。
                    println!(
                        "recv topic={} qos={:?} retain={} payload={} bytes",
                        p.topic,
                        p.qos,
                        p.retain,
                        p.payload.len()
                    );
                    if p.topic.ends_with("/ping") {
                        let _ = poller_client
                            .publish("haimen/demo/pong", QoS::AtMostOnce, false, b"pong")
                            .await;
                    }
                }
                Ok(Event::Incoming(Packet::Disconnect)) => {
                    println!("broker closed the connection");
                    break;
                }
                Ok(Event::Outgoing(Outgoing::Disconnect)) => {
                    println!("graceful disconnect sent");
                    break;
                }
                Ok(_) => {}
                Err(e) => {
                    // poll 返回错误后，下一次 poll 自动重连；退避由这里控制。
                    eprintln!("eventloop error: {e}; reconnecting in 1s");
                    time::sleep(Duration::from_secs(1)).await;
                }
            }
        }
    });

    // 4. 发布。await 只代表请求进入 EventLoop 的 channel。
    publisher
        .publish(
            "haimen/demo/up",
            QoS::AtLeastOnce,
            false,
            b"hello from haimen".as_slice(),
        )
        .await?;

    // 给 EventLoop 时间发 QoS1 并收 PUBACK。严格做法见 1.3 的 pkid 跟踪。
    time::sleep(Duration::from_millis(300)).await;

    // 5. 优雅关闭。
    publisher.disconnect().await?;
    match time::timeout(Duration::from_secs(3), &mut poller).await {
        Ok(Ok(())) => println!("shutdown clean"),
        Ok(Err(e)) => eprintln!("poller join error: {e}"),
        Err(_) => {
            eprintln!("timeout waiting for disconnect");
            poller.abort();
        }
    }
    Ok(())
}
```


## 2. AES-CTR

### 2.1 构造

`ctr` 0.9 的类型别名（`src/lib.rs`）：

```rust
pub type Ctr128BE<B> = StreamCipherCoreWrapper<CtrCore<B, flavors::Ctr128BE>>;
pub type Ctr64BE<B>  = StreamCipherCoreWrapper<CtrCore<B, flavors::Ctr64BE>>;
pub type Ctr32BE<B>  = StreamCipherCoreWrapper<CtrCore<B, flavors::Ctr32BE>>;
```

最常用：

```rust
use aes::cipher::{KeyIvInit, StreamCipher};

type Aes128Ctr = ctr::Ctr128BE<aes::Aes128>;
type Aes256Ctr = ctr::Ctr128BE<aes::Aes256>;

// AES-128-CTR：16 字节 key + 16 字节 IV
let cipher = Aes128Ctr::new(&key.into(), &iv.into());

// AES-256-CTR：32 字节 key + 16 字节 IV
let cipher = Aes256Ctr::new(&key.into(), &iv.into());
```

为什么是 `Ctr128BE` 而不是 `Ctr32BE`：

- `Ctr128BE`：整个 16 字节 IV 作为 128 位大端计数器，第一块 keystream = `AES(IV)`，第二块 = `AES(IV+1)`。适合“给定 16 字节 nonce/IV”的通用场景，也正是小智 UDP 包要的语义（PSA `PSA_ALG_CTR` 也是 128 位大端计数器）。
- `Ctr32BE`：前 12 字节是 nonce，最后 4 字节是 32 位计数器；更接近 GCM 的布局。用 12 字节 nonce 时选它，但小智协议给的是 16 字节，别选错。
- `Ctr64BE` / `Ctr32LE` 等：除非对端协议明确要求，否则不要用。

#### key / IV 的类型

`KeyIvInit`（来自 `crypto-common`，由 `cipher` re-export）：

```rust
pub trait KeyIvInit: KeySizeUser + IvSizeUser + Sized {
    fn new(key: &Key<Self>, iv: &Iv<Self>) -> Self;
    fn new_from_slices(key: &[u8], iv: &[u8]) -> Result<Self, InvalidLength>;
}
```

对 `Aes128Ctr` / `Aes256Ctr`：

| 类型 | `Key<Self>` | `Iv<Self>` |
|---|---|---|
| `Ctr128BE<Aes128>` | `GenericArray<u8, U16>`（16B） | `GenericArray<u8, U16>`（16B） |
| `Ctr128BE<Aes256>` | `GenericArray<u8, U32>`（32B） | `GenericArray<u8, U16>`（16B） |

三种写法：

```rust
// 1) 固定数组：最直观。key/iv 是 [u8; 16]
let cipher = Aes128Ctr::new(&key.into(), &iv.into());

// 2) 切片：长度运行时才知道。长度不符返回 InvalidLength
let cipher = Aes128Ctr::new_from_slices(&key_bytes, &iv_bytes)?;

// 3) 显式 GenericArray
use aes::cipher::generic_array::GenericArray;
let key_ga = GenericArray::from_slice(&key);
let iv_ga = GenericArray::from_slice(&iv);
let cipher = Aes128Ctr::new(key_ga, iv_ga);
```

注意：

- `key.into()` 能把 `[u8; 16]` 转成 `GenericArray<u8, U16>`；如果是 `&[u8; 16]`，需要 `(*key).into()` 或直接用 `new_from_slices`。
- `new_from_slices` 的 `InvalidLength` 没有具体长度信息；配置解析阶段应自己校验 `key.len() == 16/32 && iv.len() == 16`。
- `aes::cipher` 是 `cipher 0.4` 的 re-export；**不需要**在 `Cargo.toml` 里单独加 `cipher`。如果加了，版本必须是 0.4，否则 trait 不是同一个。
- `aes` 0.8 的 `Aes128` / `Aes256` 会根据 CPU 自动选择 AES-NI（x86）或软件实现；aarch64 上要启用 `aes_armv8` cfg 才走硬件指令，但 120 字节的帧软件实现也足够快。

### 2.2 加解密

CTR 是流密码：**加密和解密是同一个操作**。

```rust
use aes::cipher::{KeyIvInit, StreamCipher};

fn apply(key: &[u8; 16], iv: &[u8; 16], buf: &mut [u8]) {
    let mut cipher = Aes128Ctr::new_from_slices(key, iv).unwrap();
    cipher.apply_keystream(buf);
}

let mut data = *b"hello haimen";
apply(&key, &iv, &mut data); // 加密
apply(&key, &iv, &mut data); // 解密，恢复原文
```

#### 长度、padding 与 panic

- **无 padding**：CTR 按字节 XOR keystream，密文长度 == 明文长度。
- **空输入**：`apply_keystream(&mut [])` 是合法的，长度仍为 0。
- **非 16 字节对齐**：完全没问题；流式 wrapper 会缓存部分 block 的 keystream。
- `apply_keystream` 的文档说“到达 keystream 末尾会 panic”。`Ctr128BE` 的 keystream 长度是 `2^128` 个 block（约 `2^132` 字节），现实里不可能到达。真要有超长流，用 `try_apply_keystream()` 返回 `Result`。
- `apply_keystream` **不做认证**；密文被篡改一位，明文对应位也翻转一位。安全要求高时用 AES-GCM 或额外 HMAC。

#### 三个 inout API 的细节

`cipher 0.4` 的 `StreamCipher` trait：

```rust
pub trait StreamCipher {
    fn try_apply_keystream_inout(
        &mut self,
        buf: InOutBuf<'_, '_, u8>,
    ) -> Result<(), StreamCipherError>;

    fn apply_keystream_inout(&mut self, buf: InOutBuf<'_, '_, u8>);

    fn apply_keystream(&mut self, buf: &mut [u8]);

    fn try_apply_keystream(&mut self, buf: &mut [u8]) -> Result<(), StreamCipherError>;

    fn apply_keystream_b2b(
        &mut self,
        input: &[u8],
        output: &mut [u8],
    ) -> Result<(), StreamCipherError>;
}
```

用法：

```rust
// 原地（最常用）
cipher.apply_keystream(&mut buf);

// 输入/输出分离；长度必须相等，否则 Err(StreamCipherError)
cipher.apply_keystream_b2b(&plain, &mut ciphertext)?;

// 显式 InOutBuf：可以把同一块内存同时当输入输出
use aes::cipher::inout::InOutBuf;
let inout = InOutBuf::from(&mut buf[..]);
cipher.apply_keystream_inout(inout);

// 或者输入/输出分开
let inout = InOutBuf::new(&plain, &mut ciphertext).expect("equal lengths"); // 否则 NotEqualError
cipher.apply_keystream_inout(inout);
```

`InOutBuf` 的要点：

- `InOutBuf::from(&mut [u8])`：原地。
- `InOutBuf::new(input, output)`：长度不等返回 `NotEqualError`。
- `apply_keystream_inout` 按值接收 `InOutBuf`；借用冲突时用 `reborrow()`。
- 对普通业务，`apply_keystream` 就够了；`inout` 主要用于避免一次拷贝。

#### 流式连续性

cipher 是**有状态**的：连续调用 `apply_keystream` 会接着上次的 keystream 位置继续，包括块内偏移。

```rust
let mut cipher = Aes128Ctr::new_from_slices(&key, &iv).unwrap();
for chunk in data.chunks_mut(7) {
    cipher.apply_keystream(chunk); // 等价于一次性处理整个 data
}
```

这正是 `ctr` crate 文档里的“streaming messages”用法。但注意它的前提是**字节流可靠、有序、不丢包**（TCP）。UDP 不能这么用，见 2.3。

#### seek 与复位

```rust
use aes::cipher::StreamCipherSeek;

cipher.seek(0u64);              // 回到 keystream 起点（参数是字节偏移，不是块号）
let pos: u64 = cipher.current_pos();
cipher.seek(16u64 * 3);         // 跳到第 4 个 block 的起点
```

- `seek` 对 CTR 是 O(1)（直接改 counter），不是重新加密。
- 复用一个 cipher 处理多段独立数据时，务必 `seek(0)` 或重新 `new`，否则第二段会接着第一段的 keystream。
- `seek` 的位置是“字节偏移”；`current_pos` 返回当前已消费的字节数。

#### 安全底线

- **同一个 key + 同一个 IV 绝不能加密两段不同明文**。CTR 的 keystream 重用会直接泄露 `P1 XOR P2`。
- IV 不需要保密，但必须唯一（对每个 key）。随机 16 字节 IV 的碰撞概率在 `2^64` 个包后才需要担心；小智协议用 `sequence/timestamp` 保证唯一。
- CTR 不防篡改。生产环境若需要完整性，必须加 HMAC（先加密后 MAC，或 encrypt-then-MAC），或用 AEAD。

### 2.3 多包场景

这是最容易做错的地方。先给结论：

| 场景 | 做法 | 原因 |
|---|---|---|
| TCP / 可靠有序字节流 | **复用一个 cipher**，连续 `apply_keystream` | 对端也按同样顺序消费 keystream；丢包会由 TCP 重传 |
| UDP / 可能丢包、乱序、重复 | **每包独立初始化 cipher，IV 必须每包不同** | 丢一个包不会让后续所有包错位；也避免 keystream 重用 |
| 每包独立但 IV 固定 | ❌ 绝对禁止 | 相同 key+IV → 相同 keystream → 可恢复明文 |
| 每包独立且 IV 从包内容派生 | ✅ 推荐 | 接收端无需额外状态就能解任意包 |

#### 连续流 vs 每包独立

**连续流（一个 cipher 用到底）**：

```rust
let mut cipher = Aes128Ctr::new_from_slices(&key, &iv).unwrap();
for frame in frames {
    cipher.apply_keystream(frame); // 第 N 帧的 keystream 接着第 N-1 帧
}
```

- 优点：只初始化一次，状态连续；实现简单。
- 缺点：UDP 丢一帧，后面所有帧的 keystream 位置都对不上，全部解错。
- 只适合 TCP/WebSocket 这类可靠有序传输。

**每包独立（UDP 正确做法）**：

```rust
for (seq, frame) in frames.enumerate() {
    let packet_iv = make_unique_iv(seq); // 每包不同
    let mut cipher = Aes128Ctr::new_from_slices(&key, &packet_iv).unwrap();
    cipher.apply_keystream(frame);
}
```

- 每个包自带 IV（或能推导 IV 的字段），接收端独立解密；
- 丢包/乱序不影响其他包；
- 代价是每包一次 AES key schedule（对 120 字节来说可忽略）。

#### 小智 UDP 的真正做法：16 字节包头就是 IV

> 这节是 haimen 项目对接的关键，依据固件 `main/protocols/mqtt_protocol.cc`（[源码](https://github.com/78/xiaozhi-esp32/blob/main/main/protocols/mqtt_protocol.cc)）。

包格式：

```text
| type 1B | flags 1B | payload_len 2B | ssrc 4B | timestamp 4B | sequence 4B | payload |
|<---------------------------- 16 字节 header，同时是 AES-CTR IV --------------------------->|
```

固件发送逻辑（简化）：

```cpp
nonce = aes_nonce_;                              // 服务器 hello 下发的 16 字节模板
memcpy(nonce + 2,  &payload_len, 2);             // 覆盖 payload_len
memcpy(nonce + 8,  &timestamp, 4);               // 覆盖 timestamp
memcpy(nonce + 12, &sequence, 4);                // 覆盖 sequence
encrypted.resize(16 + payload.size());
memcpy(encrypted.data(), nonce.data(), 16);      // 前 16 字节原样发送 = header
CryptAesCtr(payload, nonce, encrypted + 16);     // IV = 整个 16 字节 nonce
```

固件接收逻辑：直接拿收到的前 16 字节当 IV 解密，同时校验 `data[0] == 0x01`、`payload_len` 与 datagram 长度一致。

**因此 Rust 服务端必须这样做**：

1. 为每个 UDP 会话生成 16 字节 key + 16 字节 nonce 模板；
2. 模板的 `[0] = 0x01`、`[1] = 0x00`、`[4..8] = ssrc`（大端）；`[2..4]` 和 `[8..16]` 可以填 0，设备会在发送时覆盖；
3. hello 响应里把 key/nonce 用 **hex 字符串**（32 个 hex 字符 = 16 字节）下发；
4. 服务端发下行包时，按同样的 header 布局构造，**用整个 header 作为 IV** 加密 payload；
5. 服务端收上行包时，用收到的前 16 字节作为 IV 解密，并校验长度/type/sequence。

对应的 Rust 实现（✅ 已验证，见 `tests/xiaozhi_packet.rs`）：

```rust
use aes::cipher::{KeyIvInit, StreamCipher};

type Aes128Ctr = ctr::Ctr128BE<aes::Aes128>;

const HEADER_LEN: usize = 16;
const PACKET_TYPE_AUDIO: u8 = 0x01;

/// 服务器下发的 16 字节 nonce 模板。
/// [0]=0x01、[1]=0x00 是 header 的 type/flags；[4..8] 是 ssrc。
/// [2..4] 和 [8..16] 会被每包的 len/timestamp/sequence 覆盖。
fn nonce_template(ssrc: u32) -> [u8; 16] {
    let mut n = [0u8; 16];
    n[0] = PACKET_TYPE_AUDIO;
    n[1] = 0;
    n[4..8].copy_from_slice(&ssrc.to_be_bytes());
    n
}

fn build_header(
    template: &[u8; 16],
    payload_len: usize,
    timestamp: u32,
    sequence: u32,
) -> [u8; 16] {
    let mut header = *template;
    header[2..4].copy_from_slice(&(payload_len as u16).to_be_bytes());
    header[8..12].copy_from_slice(&timestamp.to_be_bytes());
    header[12..16].copy_from_slice(&sequence.to_be_bytes());
    header
}

/// 加密：datagram = header || ciphertext，header 即 IV。
fn seal_packet(
    key: &[u8; 16],
    template: &[u8; 16],
    timestamp: u32,
    sequence: u32,
    plain: &[u8],
    out: &mut Vec<u8>,
) {
    assert!(plain.len() <= u16::MAX as usize, "payload too large");
    let header = build_header(template, plain.len(), timestamp, sequence);
    out.clear();
    out.reserve(HEADER_LEN + plain.len());
    out.extend_from_slice(&header);
    out.extend_from_slice(plain);
    let mut cipher = Aes128Ctr::new_from_slices(key, &header).unwrap();
    cipher.apply_keystream(&mut out[HEADER_LEN..]);
}

/// 解密：用收到的前 16 字节作为 IV；长度不变。
fn open_packet<'a>(
    key: &[u8; 16],
    packet: &'a mut [u8],
) -> Result<(u32, u32, u32, &'a mut [u8]), &'static str> {
    if packet.len() < HEADER_LEN || packet[0] != PACKET_TYPE_AUDIO {
        return Err("bad header");
    }
    let payload_len = u16::from_be_bytes([packet[2], packet[3]]) as usize;
    if packet.len() != HEADER_LEN + payload_len {
        return Err("length mismatch");
    }
    let ssrc = u32::from_be_bytes([packet[4], packet[5], packet[6], packet[7]]);
    let timestamp = u32::from_be_bytes([packet[8], packet[9], packet[10], packet[11]]);
    let sequence = u32::from_be_bytes([packet[12], packet[13], packet[14], packet[15]]);
    let (header, payload) = packet.split_at_mut(HEADER_LEN);
    let mut cipher = Aes128Ctr::new_from_slices(key, header).unwrap();
    cipher.apply_keystream(payload);
    Ok((ssrc, timestamp, sequence, payload))
}
```

验证：

```rust
#[test]
fn header_is_the_iv() {
    let key = [0x11u8; 16];
    let template = nonce_template(0xDEAD_BEEF);
    let plain = b"opus-frame-120-bytes-0123456789";
    let mut dg = Vec::new();
    seal_packet(&key, &template, 960, 1, plain, &mut dg);

    let mut rx = dg;
    let (_, _, _, payload) = open_packet(&key, &mut rx).unwrap();
    assert_eq!(payload, plain);
    assert_eq!(rx[0], 0x01);
    assert_eq!(rx.len(), 16 + plain.len());
}
```

**几个非常容易错的点**：

1. **不要把 hello 下发的 `nonce` 直接当成固定 IV 用 `Ctr128BE::new(key, nonce)` 加密整条流。** 固件是每包把 `len/timestamp/sequence` 写进 nonce 再用；固定 IV 会导致 keystream 重用。
2. **nonce 模板的 `[0]` 必须是 `0x01`，`[4..8]` 必须是 ssrc。** 固件直接把模板当 header 的前 16 字节发送，只覆盖 `[2..4]` 和 `[8..16]`；如果 `[0]` 是随机值，设备发出的包 type 就不是 0x01，接收端会丢。
3. **`payload_len` 是 Opus payload 长度，不含 16 字节头。** 密文长度 = `payload_len`，datagram 长度 = `16 + payload_len`。无 padding。
4. **`sequence` 每包递增**；固件 `++local_sequence_` 后使用，第一包是 1；接收端拒绝 `sequence <= remote_sequence_`。服务端每个新会话要把期望序号重置为 0（或 1 起）。
5. **`timestamp` 按毫秒使用**（协议字段本身未注明单位；haimen 的 `ws.rs` 里每帧 `+= frame_duration`，60ms 一帧）。它参与 IV，所以同一毫秒内发多帧也必须靠 sequence 区分；不要用固定 timestamp。
6. **key/nonce 是 hex 字符串**，`32` 个字符；固件 `DecodeHexString` 只接受偶数长度合法 hex。
7. **sequence/timestamp 32 位回绕**：`u32` 序列号约 49.7 天回绕（按 1ms 计）；实现里用 `wrapping_add`，重放窗口也要能处理回绕。实际会话生命周期远短于此，但不要用 `checked_add().unwrap()` 把进程 panic 掉。
8. **重连/重新 hello 必须换 key/nonce**：固件在 `OpenAudioChannel` 时销毁旧 PSA key、重置 `local_sequence_/remote_sequence_`。服务端也应把旧会话的 key 作废，避免跨会话 IV 重用。
9. **UDP 丢包时不要用连续 cipher**：上面这个方案每包 IV 独立，丢包不会影响其他包；这正是它适合 UDP 的原因。
10. **CTR 无完整性**：小智协议本身只保密不认证；如果 haimen 要防篡改，需要在 payload 内加 HMAC 或换 AEAD（但固件不支持，故只能接受“局域网 + 序列号防重放”的安全边界）。

## 3. 实时音频下的非阻塞设计

### 3.1 60ms / 120 字节做 AES-CTR 有问题吗？

没有。粗算：

- 120 字节 = 7.5 个 AES block（8 个 block 的 keystream）；
- 每 60ms 一次，即 16.7 帧/s；
- AES-CTR 吞吐通常是数百 MB/s 到 GB/s 量级；120 字节的加密成本在**亚微秒到几微秒**；
- 每帧的分配、加锁、系统调用、MQTT 排队，通常比 AES 本身贵得多。

所以：

- **不需要** `spawn_blocking`；
- **不需要** 为 AES 单独开线程；
- 需要关注的是**不要在音频循环里做会阻塞/挂起的操作**（`publish().await`、同步锁、文件 IO、DNS、日志刷盘）。

> ⚠️ 需验证：目标硬件（ARM 路由器/低端设备）上的实际耗时。建议在目标板跑一次 `criterion` 或简单 `Instant::now()` 统计 P99；只要单帧 < 1ms 就完全不影响 60ms 节奏。

### 3.2 `publish()` 是同步非阻塞的吗？

不是“同步非阻塞”，而是**异步但通常很快就返回**：

```rust
pub async fn publish(...) -> Result<(), ClientError> {
    ...
    self.request_tx.send_async(publish).await?; // 关键：这里可能 await
    Ok(())
}
```

- 如果 EventLoop 正常 poll 且 channel 有空间：`send_async` 立即完成，通常只 poll 一次 Future，不会让出线程太久；
- 如果 channel 满（EventLoop 卡住/网络断/发布太快）：**它会挂起等待**，直到有空位或 channel 关闭；
- 如果 EventLoop 已经退出：立即返回 `ClientError::Request(..)`。

所以：

- 控制面（HA 指令、状态上报）可以用 `publish().await`，让背压自然传导；
- **实时音频循环不要 `await publish()`**。用 `try_publish()`（同步、立即返回）或把帧丢给专用网络 task 的 `mpsc`，音频循环只做 `try_send`。

`try_publish()` 是真正的同步非阻塞：内部 `try_send`，满/断连都立即返回 `Err`。

### 3.3 MQTT 事件转 channel 的推荐模式

| channel | 语义 | 适用 |
|---|---|---|
| `tokio::sync::mpsc` | 多生产者、单消费者；有界时提供背压 | 音频帧、控制指令、事件队列 |
| `tokio::sync::watch` | 只保留最新值；新订阅者立刻拿到当前值 | 配置热更新（key/音量/目标地址/静音）、连接状态 |
| `tokio::sync::broadcast` | 多消费者广播；慢消费者会 `Lagged` | 一份事件给多个模块（录制 + 发送 + 监控） |
| `tokio::sync::oneshot` | 一次性请求/响应 | 握手、确认某个命令完成 |

推荐拓扑：

```text
┌──────────────┐   mpsc<Vec<u8>>   ┌──────────────────┐   try_publish   ┌──────────────┐
│ 采集/解码 task│ ────────────────> │ 加密 + 网络 task  │ ──────────────> │ MQTT EventLoop│
└──────────────┘  (bounded, drop)  └──────────────────┘                 └──────┬───────┘
                                                                               │ Incoming(Publish)
                                                                               v
┌──────────────┐   mpsc<Command>   ┌──────────────────┐   watch<Config>  ┌──────────────┐
│ 会话状态机    │ <──────────────── │ MQTT 事件分发 task│ ───────────────> │ 音频/会话 task│
└──────────────┘                   └──────────────────┘                  └──────────────┘
```

原则：

- **每条跨 task 的队列都要有界**；无界队列会把“网络慢”变成“内存涨”。
- 音频帧队列满了**丢旧帧/丢新帧**，不要阻塞采集；实时性优先。
- 配置用 `watch`，不要用 `mpsc` 发“最新配置”，否则会积压过期配置。
- 一份事件确实要给多个消费者才用 `broadcast`；否则 `mpsc` 更简单。
- MQTT 事件循环只做解析/分发，不在里面做 ASR/LLM/TTS。

### 3.4 音频循环骨架

> ✅ 已验证：同样的 `interval` + `try_recv` + `try_publish` 模式在 `udp_audio.rs` 中编译/运行通过；下面把 MQTT 换成了真实的 `AsyncClient`。

```rust
use std::time::Duration;

use aes::cipher::{KeyIvInit, StreamCipher};
use rumqttc::{AsyncClient, QoS};
use tokio::sync::mpsc;
use tokio::time::MissedTickBehavior;

type Aes128Ctr = ctr::Ctr128BE<aes::Aes128>;

/// 同 2.3：header = type|flags|len|ssrc|timestamp|sequence
fn build_header(template: &[u8; 16], payload_len: usize, timestamp: u32, sequence: u32) -> [u8; 16] {
    let mut h = *template;
    h[2..4].copy_from_slice(&(payload_len as u16).to_be_bytes());
    h[8..12].copy_from_slice(&timestamp.to_be_bytes());
    h[12..16].copy_from_slice(&sequence.to_be_bytes());
    h
}

enum Command {
    Start,
    Stop,
    SetMute(bool),
}

async fn audio_loop(
    mqtt: AsyncClient,
    mut pcm_rx: mpsc::Receiver<Vec<u8>>,
    mut cmd_rx: mpsc::Receiver<Command>,
    mut config_rx: tokio::sync::watch::Receiver<AudioConfig>,
) {
    let mut ticker = tokio::time::interval(Duration::from_millis(60));
    ticker.set_missed_tick_behavior(MissedTickBehavior::Delay); // 落后就跳过，不补发

    let mut cfg = (*config_rx.borrow()).clone();
    let mut seq: u32 = 1;
    let mut ts: u32 = 0;
    let mut out = Vec::with_capacity(16 + 120);

    loop {
        ticker.tick().await;

        // 1) 控制命令：非阻塞，最多处理当前积压
        while let Ok(cmd) = cmd_rx.try_recv() {
            match cmd {
                Command::Start => { /* ... */ }
                Command::Stop => { /* ... */ }
                Command::SetMute(m) => { /* ... */ }
            }
        }

        // 2) 配置热更新：只取最新值
        if config_rx.has_changed().unwrap_or(false) {
            cfg = (*config_rx.borrow_and_update()).clone();
            // 更新 key/ssrc/target 等；换 key 时应同时把 seq/ts 归零，
            // 并与对端重新握手，避免跨 key 重用 IV。
        }

        // 3) 音频帧：只保留最新一帧，丢掉过期积压，控制延迟
        let mut latest = None;
        while let Ok(frame) = pcm_rx.try_recv() {
            latest = Some(frame);
        }
        let Some(pcm) = latest else { continue };

        // 4) 加密（原地/复用 buffer，避免每帧分配）
        let header = build_header(&cfg.template, pcm.len(), ts, seq);
        out.clear();
        out.extend_from_slice(&header);
        out.extend_from_slice(&pcm);
        let mut cipher = Aes128Ctr::new_from_slices(&cfg.key, &header).unwrap();
        cipher.apply_keystream(&mut out[16..]);

        // 5) 非阻塞投递 MQTT；满/断连就丢帧（实时音频的正确取舍）
        if let Err(e) = mqtt.try_publish(
            "haimen/xiaozhi/device/udp",
            QoS::AtMostOnce,
            false,
            out.clone(), // try_publish 需要 owned；可改成 Bytes/池化减少拷贝
        ) {
            eprintln!("mqtt busy, drop audio frame: {e}");
        }

        seq = seq.wrapping_add(1);
        ts = ts.wrapping_add(60);
    }
}

#[derive(Clone)]
struct AudioConfig {
    key: [u8; 16],
    template: [u8; 16],
}
```

要点：

- `MissedTickBehavior::Delay`：如果某次 tick 被阻塞，下一次从“现在”重新计时，不会 burst 补帧。实时音频要的是“最新”，不是“补课”。
- `try_recv` 只处理已到达的帧；不要 `recv().await` 在 tick 里等。
- 音频帧“只保留最新”是低延迟策略；如果你需要连续音频，必须保证采集/编码/发送都不阻塞，并接受丢帧。
- `out.clone()` 每帧一次分配；120 字节可接受。极致优化可用 `bytes::Bytes` + `publish_bytes` 或对象池，但不要为了 120 字节引入复杂生命周期。
- 不要在循环里 `println!` 每帧打印；日志本身可能阻塞。

### 3.5 什么时候需要 `spawn_blocking`？

需要满足“**阻塞**”而不是“耗时”：

| 场景 | 是否需要 |
|---|---|
| 120 字节 AES-CTR | ❌ 不需要 |
| Opus 编解码（单帧） | ❌ 通常不需要（微秒~百微秒） |
| 同步文件读写、SQLite、`std::fs` | ✅ 需要（或换 tokio 异步 API） |
| 同步 HTTP/DNS/阻塞库 | ✅ 需要 |
| 大模型推理 / 图像处理 / 单次 > 1ms 的 CPU | ✅ 需要，且要考虑专用线程池 |
| 硬实时音频回调（cpal） | ❌ 不要用 `spawn_blocking`；用 lock-free ring buffer + 独立 task |

注意：

- `spawn_blocking` 不是“实时线程”，它的调度延迟可能几毫秒；不要指望它保证 60ms 节奏。
- `spawn_blocking` 任务不能被取消；大量堆积会耗尽 blocking pool。
- 在 tokio worker 里直接做阻塞操作，会卡住整个 runtime 的调度；这比 AES 慢更严重。
- 如果音频回调是独立的 OS 线程（cpal），**绝对不要**在回调里 `block_on`、`spawn`、加 tokio 锁、分配大内存或写日志；用 `ringbuf`（或 `crossbeam`）把数据交给 tokio task。

### 3.6 MQTT 传音频的现实建议

小智协议本身是“MQTT 控制 + UDP 音频”。**不要把音频塞进 MQTT**，除非只是调试：

- TCP 队头阻塞：一个 QoS1 重传会卡住后面所有音频；
- QoS1/2 的重传会制造延迟尖峰；
- MQTT broker 的持久化/限流不是为 60ms 实时流设计的。

如果必须用 MQTT 传音频帧：

- 用 QoS0；
- 帧小（< 1KB），不要攒大包；
- 丢帧优于补发；
- 不要依赖 broker 的离线队列。

## 4. UDP socket 模式

### 4.1 基本收发

```rust
use std::net::SocketAddr;
use tokio::net::UdpSocket;

let socket = UdpSocket::bind("0.0.0.0:8888").await?;
let mut buf = [0u8; 2048];

// 收：返回 (实际字节数, 源地址)
let (n, from): (usize, SocketAddr) = socket.recv_from(&mut buf).await?;

// 发：返回实际写入的字节数（UDP 上通常等于 buf.len()）
let sent = socket.send_to(&buf[..n], from).await?;
```

精确签名：

```rust
pub async fn recv_from(&self, buf: &mut [u8]) -> io::Result<(usize, SocketAddr)>;
pub async fn send_to<A: ToSocketAddrs>(&self, buf: &[u8], target: A) -> io::Result<usize>;
```

注意：

- `recv_from` 的 `buf` 不够大时，超出部分会被截断（不同平台行为略有差异）；音频包 120B，用 2048B 足够；不确定时用 64KB。
- `send_to` 返回的字节数在 UDP 上通常等于输入长度；不要用“返回值 < len”判断部分发送（UDP 是整包）。
- `recv_from` 是 cancel-safe 的：在 `select!` 里被取消不会丢包（tokio 文档保证）。但你的业务解析要能处理“一次只读到一个包”。

### 4.2 一个 socket 同时收和发

`UdpSocket` 的 `recv_from` / `send_to` 都只借 `&self`，所以可以：

```rust
use std::sync::Arc;

let socket = Arc::new(UdpSocket::bind("0.0.0.0:8888").await?);

// 收包 task
let rx = socket.clone();
tokio::spawn(async move {
    let mut buf = [0u8; 2048];
    loop {
        match rx.recv_from(&mut buf) {
            Ok((n, from)) => { /* parse + dispatch */ }
            Err(e) => eprintln!("udp recv error: {e}"),
        }
    }
});

// 任意 task 发包
socket.send_to(&datagram, peer).await?;
```

要点：

- **不需要 `split()`**；`Arc<UdpSocket>` 就够了。
- 多个 task 并发 `send_to` 是安全的；UDP 不保证跨 task 的发送顺序，靠包头 sequence 排序。
- 如果要“只和固定对端通信”，可以 `socket.connect(peer).await?`，之后用 `send`/`recv`；但**多设备场景不要 connect**，否则一个 socket 只能对一个对端。
- 绑定 `0.0.0.0:port` 接收所有网卡；对外通告地址时不要用 `0.0.0.0`，要用局域网 IP：

```rust
let ip = local_ip_address::local_ip()?; // ✅ 已验证 0.6.13 可编译
let advertised = format!("{ip}:8888");
```

> ⚠️ 需验证：多网卡/ VPN 环境下 `local_ip()` 选中的网卡是否是设备可达的那张；生产建议允许配置显式 `udp.server` 覆盖。

### 4.3 多设备共用一个 UDP 端口：怎么区分？

推荐同时使用 **源地址 + 包头 ssrc**：

| 标识 | 稳定性 | 用途 |
|---|---|---|
| `SocketAddr`（源 IP:port） | 可能因 NAT 重绑定/漫游变化 | 回包地址；首包识别 |
| `ssrc`（4 字节） | 会话内稳定；由服务器分配或设备上报 | 会话主键；多路复用 |
| `key/nonce`（每会话） | 会话内稳定 | 解密；天然区分不同会话 |
| 设备 ID / MAC（MQTT 层） | 最稳定 | 业务身份；与 ssrc 绑定 |

小智的包已经带了 `ssrc`，所以：

```rust
struct Session {
    device_id: String,
    ssrc: u32,
    peer: SocketAddr,
    key: [u8; 16],
    template: [u8; 16],
    last_seq: u32,
    last_seen: Instant,
}

struct UdpMux {
    by_ssrc: HashMap<u32, Session>,
    by_addr: HashMap<SocketAddr, u32>,
}
```

收包流程：

1. `recv_from` 拿到 `(n, from)`；
2. 解析 16 字节头，校验 `type == 0x01`、`len`、datagram 长度；
3. 用 `ssrc` 查会话；查不到再看 `by_addr`（首包/NAT 重绑定）；
4. 用会话的 key + 包头 IV 解密；
5. 校验 `sequence`（重放窗口/丢包统计）；
6. 更新 `peer = from`（允许 NAT 端口变化，但要限速/校验，防劫持）；
7. 把 payload 投递给会话 task。

发包流程：

1. 用 `ssrc` 查会话；
2. 构造 header（type/flags/len/ssrc/timestamp/sequence）；
3. `seal_packet`；
4. `socket.send_to(&datagram, session.peer)`。

安全注意：

- `ssrc` 不是认证凭据，可伪造；**CTR 解密永远会“成功”**（任何密文都能 XOR 出明文），它不能证明对方知道 key，也不能防篡改。
- 局域网方案可以接受“key 保密 + 序列号防重放”的安全边界；公网必须加 HMAC/DTLS。
- `by_addr` 的更新要谨慎：如果攻击者从新地址发一个同 ssrc 的包，不能直接把 `peer` 改过去；至少要求序列号在窗口内且会话上下文匹配（CTR 解密本身不提供认证），最好有握手 token。
- 会话超时清理：`last_seen` 超过 N 秒（例如 30s）删除；同时清理 `by_addr` 反向索引。

### 4.4 推荐的单 socket 多设备复用模式

```text
                    ┌─────────────────────────────┐
   device A ───────>│                             │
   device B ───────>│  Arc<UdpSocket> 0.0.0.0:8888 │
   device C ───────>│                             │
                    └──────────────┬──────────────┘
                                   │ recv_from
                                   v
                    ┌─────────────────────────────┐
                    │ 1 个 recv task               │
                    │  parse header                │
                    │  ssrc -> Session             │
                    │  decrypt (header = IV)       │
                    │  seq/replay check            │
                    └──────────────┬──────────────┘
                                   │ mpsc<InboundFrame>
                                   v
                    ┌─────────────────────────────┐
                    │ N 个 per-session task        │
                    │  jitter buffer / 解码 / 业务  │
                    └──────────────┬──────────────┘
                                   │ send_to (Arc clone)
                                   v
                            同一个 UdpSocket
```

实现建议：

- **一个端口一个 recv task**，不要为每个设备开 socket（端口爆炸、NAT 难配）。
- recv task 只做“解析 + 解密 + 路由”，不做 Opus 解码/ASR；用有界 `mpsc` 分发给 per-session task。
- 发送用同一个 `Arc<UdpSocket>`；`send_to` 是 `&self`，不需要锁。
- 如果发送频率很高，考虑 `try_send_to`（tokio 1.x 提供）避免 await；但 UDP 发送一般不会阻塞太久。
- 每个 session 的 key/nonce 独立；**不要所有设备共用一把 key**（否则 ssrc/IV 管理稍错就跨设备 keystream 重用）。
- 会话建立时记录 `(device_id, ssrc, peer, key, template)`；MQTT 的 `hello` 与 UDP 首包要能关联（用 ssrc 或 session_id）。
- 设备重启后 ssrc 可能变；用 MQTT `hello` 重新绑定，旧会话超时清理。

### 4.5 UDP 的丢包/乱序/重复

- 音频包带 `sequence`，接收端做**滑动窗口**：
  - 窗口内已收到的包丢弃（重复）；
  - 窗口外太旧的包丢弃（重放/延迟）；
  - 窗口内缺口允许等待一小段时间（jitter buffer），超时用 PLC（丢帧补偿）跳过。
- 固件接收端比较严格：`sequence <= remote_sequence_` 直接丢；`sequence != remote_sequence_ + 1` 只告警但仍处理。服务端发下行时要按序发，别让设备丢包。
- UDP 没有重传；丢了就丢了。实时音频靠 PLC/FEC/丢帧，不靠重传。
- 包大小控制在 MTU 内：IPv6 最小 MTU 1280，减去 IP/UDP 头，payload 建议 < 1200 字节；120 字节的 Opus 帧完全没问题。

### 5.3 rumqttc 的 mock

#### 方案 A：进程内 mock broker（推荐，无需外部依赖）

> ✅ 已验证：`cargo test --test mqtt_smoke` 通过，覆盖 CONNECT/CONNACK、SUBSCRIBE/SUBACK、PUBLISH/PUBACK、PINGREQ/PINGRESP、DISCONNECT。

```rust
// tests/mqtt_smoke.rs
use std::time::Duration;

use rumqttc::{AsyncClient, Event, MqttOptions, Outgoing, Packet, QoS};
use tokio::io::{AsyncReadExt, AsyncWriteExt};
use tokio::net::{TcpListener, TcpStream};
use tokio::sync::mpsc;
use tokio::time::timeout;

/// 读一个完整 MQTT 包：fixed header + remaining length + body。
async fn read_packet(stream: &mut TcpStream) -> std::io::Result<Option<Vec<u8>>> {
    let mut first = [0u8; 1];
    if stream.read_exact(&mut first).await.is_err() {
        return Ok(None);
    }
    let mut packet = vec![first[0]];
    let mut remaining = 0usize;
    let mut multiplier = 1usize;
    loop {
        let mut b = [0u8; 1];
        stream.read_exact(&mut b).await?;
        packet.push(b[0]);
        remaining += ((b[0] & 0x7f) as usize) * multiplier;
        if b[0] & 0x80 == 0 {
            break;
        }
        multiplier *= 128;
    }
    let mut body = vec![0u8; remaining];
    stream.read_exact(&mut body).await?;
    packet.extend_from_slice(&body);
    Ok(Some(packet))
}

fn body_start(packet: &[u8]) -> usize {
    let mut i = 1;
    while packet[i] & 0x80 != 0 {
        i += 1;
    }
    i + 1
}

/// 极简 broker：只处理本测试需要的包。
async fn mock_broker(listener: TcpListener) -> std::io::Result<()> {
    let (mut stream, _) = listener.accept().await?;
    while let Some(packet) = read_packet(&mut stream).await? {
        let kind = packet[0] >> 4;
        let body = &packet[body_start(&packet)..];
        match kind {
            1 => stream.write_all(&[0x20, 0x02, 0x00, 0x00]).await?, // CONNACK success
            8 => {
                // SUBSCRIBE: pkid(2) + filter...
                let pkid = u16::from_be_bytes([body[0], body[1]]);
                stream
                    .write_all(&[0x90, 0x03, (pkid >> 8) as u8, pkid as u8, 0x01])
                    .await?; // SUBACK, 授予 QoS1
            }
            3 => {
                // PUBLISH: topic(2+n) + [pkid(2) if qos>0] + payload
                let qos = (packet[0] >> 1) & 0x03;
                let topic_len = u16::from_be_bytes([body[0], body[1]]) as usize;
                let mut i = 2 + topic_len;
                if qos > 0 {
                    let pkid = u16::from_be_bytes([body[i], body[i + 1]]);
                    i += 2;
                    stream
                        .write_all(&[0x40, 0x02, (pkid >> 8) as u8, pkid as u8])
                        .await?; // PUBACK
                }
                let payload = &body[i..];
                let topic = b"haimen/demo/down";
                let mut out = vec![0x30, (2 + topic.len() + payload.len()) as u8];
                out.extend_from_slice(&(topic.len() as u16).to_be_bytes());
                out.extend_from_slice(topic);
                out.extend_from_slice(payload);
                stream.write_all(&out).await?;
            }
            12 => stream.write_all(&[0xd0, 0x00]).await?, // PINGRESP
            14 => break,                                  // DISCONNECT
            _ => {}
        }
    }
    Ok(())
}

#[tokio::test]
async fn connect_subscribe_publish_and_graceful_disconnect() {
    let listener = TcpListener::bind("127.0.0.1:0").await.unwrap();
    let addr = listener.local_addr().unwrap();
    let broker = tokio::spawn(mock_broker(listener));

    let mut options = MqttOptions::new("haimen-test", addr.ip().to_string(), addr.port());
    options
        .set_keep_alive(Duration::from_secs(5))
        .set_clean_session(true)
        .set_credentials("user", "pass");
    let (client, mut eventloop) = AsyncClient::new(options, 16);
    let publisher = client.clone();

    let (tx, mut rx) = mpsc::channel::<Vec<u8>>(4);
    let poller = tokio::spawn(async move {
        loop {
            match eventloop.poll().await {
                Ok(Event::Incoming(Packet::ConnAck(_))) => {
                    client
                        .subscribe("haimen/demo/#", QoS::AtLeastOnce)
                        .await
                        .unwrap();
                }
                Ok(Event::Incoming(Packet::Publish(p))) => {
                    tx.send(p.payload.to_vec()).await.unwrap();
                }
                Ok(Event::Outgoing(Outgoing::Disconnect)) => break,
                Ok(_) => {}
                Err(e) => panic!("eventloop error: {e}"),
            }
        }
    });

    publisher
        .publish("haimen/demo/up", QoS::AtLeastOnce, false, b"hello".as_slice())
        .await
        .unwrap();

    let echoed = timeout(Duration::from_secs(3), rx.recv())
        .await
        .expect("timeout waiting for publish")
        .expect("channel closed");
    assert_eq!(echoed, b"hello");

    publisher.disconnect().await.unwrap();
    timeout(Duration::from_secs(3), poller)
        .await
        .expect("poller timeout")
        .unwrap();
    timeout(Duration::from_secs(3), broker)
        .await
        .expect("broker timeout")
        .unwrap()
        .unwrap();
}
```

优点：不依赖外部 broker，CI 可跑；能精确注入“断开/延迟/重复包”。缺点：只实现了测试需要的 MQTT 子集，不能替代真实 broker 的兼容性测试。

#### 方案 B：`#[ignore]` + 真实 broker

```rust
    options.set_keep_alive(Duration::from_secs(10));
    let (client, mut eventloop) = AsyncClient::new(options, 16);

    let poller = tokio::spawn(async move {
        loop {
            match eventloop.poll().await {
                Ok(_) => {}
                Err(e) => panic!("{e}"),
            }
        }
    });

    client.subscribe("haimen/it/#", QoS::AtLeastOnce).await.unwrap();
    client.publish("haimen/it/x", QoS::AtLeastOnce, false, b"ok").await.unwrap();
    tokio::time::sleep(Duration::from_millis(300)).await;
    client.disconnect().await.unwrap();
    poller.abort();
}
```

#### 方案 C：`AsyncClient::from_senders`（不推荐）

`AsyncClient::from_senders(request_tx: flume::Sender<Request>)` 可以构造一个假 client，然后直接检查请求 channel 里的 `Request`。但：

- 需要直接依赖 `flume = "0.11"`，且必须与 rumqttc 内部版本一致；
- `Request` 是 rumqttc 内部协议类型，升级易碎；
- 只能测“请求长什么样”，测不了 EventLoop 的 ack/重连行为。

只适合临时调试，不建议作为主测试方案。

#### 方案 D：给业务加 trait 边界

如果只想测业务状态机，不要把 `AsyncClient` 传进去；定义：

```rust
#[async_trait::async_trait]
trait MqttSink: Send + Sync {
    async fn publish_json(&self, topic: &str, value: &serde_json::Value) -> anyhow::Result<()>;
}
```

生产实现包 `AsyncClient`，测试用 `Vec<Value>` 记录调用。这样 90% 的业务逻辑不需要 broker。

### 5.4 重连测试

让 mock broker 支持多次 accept。下面**是伪代码**，`serve` 复用 5.3 里 `mock_broker` 的循环；重点是“第一次连接 CONNACK 后立刻 close，第二次正常服务”，然后断言客户端重连并重新订阅。

```rust
async fn mock_broker_multi(listener: TcpListener, drops: usize) {
    for i in 0..=drops {
        let (mut stream, _) = listener.accept().await.unwrap();
        // 第一个连接：CONNACK 后直接 close，模拟断线
        if i < drops {
            let _ = read_packet(&mut stream).await; // CONNECT
            stream.write_all(&[0x20, 0x02, 0x00, 0x00]).await.unwrap();
            drop(stream);
        } else {
            // 正常服务
            serve(&mut stream).await;
        }
    }
}
```

断言：

- 第二次 `ConnAck` 出现；
- 订阅请求再次出现（mock broker 记录 `SUBSCRIBE` 次数）；
- 退避时间递增（用 `tokio::time::pause` 或记录 `Instant`）。

### 5.5 UDP 测试

```rust
#[tokio::test]
async fn udp_loopback_round_trip() {
    let a = tokio::net::UdpSocket::bind("127.0.0.1:0").await.unwrap();
    let b = tokio::net::UdpSocket::bind("127.0.0.1:0").await.unwrap();
    let b_addr = b.local_addr().unwrap();

    let key = [0x11u8; 16];
    let template = nonce_template(0x1234_5678);
    let mut dg = Vec::new();
    seal_packet(&key, &template, 960, 1, b"hello", &mut dg);

    a.send_to(&dg, b_addr).await.unwrap();
    let mut buf = [0u8; 2048];
    let (n, from) = b.recv_from(&mut buf).await.unwrap();
    assert_eq!(from, a.local_addr().unwrap());
    let (ssrc, ts, seq, payload) = open_packet(&key, &mut buf[..n]).unwrap();
    assert_eq!((ssrc, ts, seq), (0x1234_5678, 960, 1));
    assert_eq!(payload, b"hello");
}
```

多设备路由测试：两个 socket 用不同 ssrc 发到同一端口，断言 `UdpMux` 路由到不同 session、回包地址正确。丢包/乱序测试：直接构造乱序 sequence 的包，断言 jitter buffer 行为。

## 附录 B：haimen 对接清单

- [ ] `crates/haimen-xiaozhi/Cargo.toml` 已有 `rumqttc` / `aes` / `ctr` / `local-ip-address` workspace 依赖（已确认）。
- [ ] client_id 用设备 MAC（保证多设备不互踢）；不要用固定字符串。
- [ ] keepalive 按 OTA 下发值（小智默认 240s）；不要用 <1s。
- [ ] `clean_session`：设备侧协议未要求持久会话时用 `true`，并在每次 ConnAck 后重订阅。
- [ ] 订阅设备 `publish_topic`；向设备下行 topic 发布。topic 命名需以真机抓包为准。
- [ ] MQTT payload 是 JSON 文本；`serde_json` 处理；不要假设 payload 是 UTF-8 之外的内容。
- [ ] hello 响应里 `udp.key` / `udp.nonce` 用 **hex**（32 字符 = 16 字节）。
- [ ] nonce 模板：`[0]=0x01`、`[1]=0x00`、`[4..8]=ssrc`；否则设备发出的包 type 不对。
- [ ] UDP 服务端绑定 `0.0.0.0:port`，hello 里通告 `local_ip()` 得到的局域网地址（不要 0.0.0.0）。
- [ ] 每个会话独立 key/nonce/ssrc；重连/重新 hello 必须换 key 并把 sequence 重置。
- [ ] 每个 UDP 包：header = IV；`payload_len` 不含 16B 头；无 padding。
- [ ] sequence 从 1 开始递增；接收端做重放窗口；32 位回绕用 `wrapping_add`。
- [ ] timestamp 每帧 +60（与 `ws.rs` 的 `cumulated_timestamp` 一致），参与 IV。
- [ ] 单 UDP socket 用 `Arc<UdpSocket>`，一个 recv task 解析/解密/路由，发送用 `send_to`。
- [ ] 多设备用 `ssrc` 主键 + 源地址回包；NAT 重绑定要校验后再更新；会话超时清理。
- [ ] 音频循环不 `await publish()`；用 `try_publish()` 或有界 `mpsc` + 丢帧。
- [ ] 音频帧加密/解密不 `spawn_blocking`；避免在音频循环里分配/加锁/日志。
- [ ] AES-CTR 只保密不认证；局域网可接受，公网必须加 HMAC/DTLS 或换 AEAD。
- [ ] 测试：NIST 向量、round-trip、header-IV、mock broker、UDP loopback；真机测试用 `#[ignore]` 隔离。
